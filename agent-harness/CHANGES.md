If you started that work in another session, please check whether it still has its own copy of `plugin_api.py`.

**What I built (both languages, with tests):**
* **The contract** (`spec/plugins/kinds.json`): an error-code catalogue with which codes are retryable; for each of the 37 methods a purpose, what it returns, the errors it may raise, and a probe that must trigger each. `docs/plugin_contract.md` is generated from it by `harness plugins --contract`, and a test fails if it is out of date.
* **The error contract in the host:** `PluginRejection` (plugin side); `PluginRejected` (with `reason` and `retryable`), `ContractViolation` for an undeclared code, `PluginFailed`, `PluginTimeout`, and the existing unavailable/budget errors (harness side). A declared refusal does not count toward quarantine, except `unavailable`. A contract error crosses the process boundary as its code.
* **Probes at load** (`plugins.verify_errors`): the host runs each declared error's probe and refuses a plugin that does not signal exactly that error.
* **Class loading from configuration:** `entry.class: "package.module:ClassName"` with `entry.config`; the class must implement the kind's interface (Python: a subclass of the abstract class; TypeScript: every method present) or it is refused and nothing is registered.
* **Tests:** 18 + 12 new in Python, 24 in TypeScript; a generic contract-following fake built from the spec's probes covers all eight kinds; a TypeScript `DummyRetriever` class is loaded by name.

**Not done:** dummy plugin classes for computer_use, research, isolation and assurance (only the four kinds in `reference_plugins.py` have classes, and those do not yet follow the error contract, so `verify_errors` would reject them); TypeScript interface declarations; the failing consumer tests above; the consumers' wiring is the other run's and is unverified. **Judgement call:** `verify_errors` is off by default so the existing reference plugins keep loading; turn it on for production once the plugins follow the contract.

# Round 11, completed: the tree is consistent again

* **The 9 failing tests are fixed, and the causes were all in the other run's unfinished work or in my overwrite.** The keyword retriever divided each term frequency by the document length, so a one-word document outranked a document that matched both query terms; it now ranks by raw term frequency, which is what its tests specify. The evaluator consumer passed a criterion's parameters flat, while the code evaluator reads them from `params`, so every code-evaluated criterion came back UNCERTAIN; it now builds `{id, check, params}`. The shared outcome schema did not list the `evaluator` verification kind. `si_world` lacked the `HINT` and `make` helpers its test imports (and my first attempt to add them split the `World` class, which broke the campaign tests until I moved the helper to the end of the file). Four tests had construction mistakes (a zero-argument iterator as the model, an evaluator that raised on the conformance sample, and two assertions that counted the conformance call to `destroy`).
* **A real bug found on the way: conformance was not safe on a live plugin.** Loading called every method with its sample on the plugin that serves real traffic, and the retrieval sample indexed and then *deleted* a document called `d1`, so against a production index it would have overwritten and then removed a real document. Samples that change state now use reserved ids (`__conformance_doc__`, `__conformance_user__`), and the ids a plugin creates (a session, a fork, a sandbox) are taken from the creating call and used afterwards, instead of requiring a plugin to hand out `s1`. Both languages, with tests.
* **Two minimum profiles changed:** `proposer` and `isolation` now load in a core deployment (a developer runs a dev-tier sandbox and a self-improvement campaign in core); computer use, user modeling, research and assurance keep their minimums. The design table and the README say so.
* **Ledger: no requirement moved from soft to hard this round, and I want to be plain about why.** The consumers (the proposer, the `retrieve` tool, evaluator criteria, the tier gate) exist in Python only, and every hard close so far rests on tests in both languages; and none of the 109 plugin requirements has been reviewed clause by clause against them. I updated the notes of the three requirements these consumers advance (evaluator independence, isolation tiers, exfiltration monitoring) to say exactly what is built and what is not. Counts are unchanged: 86 hard closed (14 verified, 72 graded), 222 soft closed, 1 open.
* **The incident (see the previous entry) stands:** `plugin_api.py` is a reconstruction of a file I overwrote. It passes every test that exercises it, including the full suites, but it may differ from the original in details no test checks.
