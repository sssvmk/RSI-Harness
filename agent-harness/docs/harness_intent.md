# Product Requirements Document: AI Agent Harness (Platform Runtime, Control Plane & Self-Improvement)

## 1. Executive Summary
This document outlines the architectural and functional requirements for an enterprise-grade Agent Harness. The harness serves as the control plane that surrounds a language model, managing state, context, execution boundaries, and multi-step loops to enable reliable, long-running agentic work.

**Scope and relationship to the companion PRD.** This document is the foundation specification and applies to every deployment, whether single-agent or multi-agent. It owns all requirements that must hold even when only one agent is running: loop control, context and memory, tools, MCP, approvals, containment, observability, durability, evaluation principles, and configuration governance. Requirements that exist only because multiple agents interact (topology, channels, handoffs, inter-agent trust, and dynamic team pruning) are specified in the companion *Multi-Agent System PRD* (`multi_agents_system.md`), which depends on this document. This document also owns how the harness improves itself and under what governance: self-modification governance, the improvement loop, its evaluation protocol, and optimization methods such as declarative compilation, prompt and system optimization, and learned proposers (§6). It also owns the single-agent capabilities that agents use: knowledge retrieval (§8), computer use (§9), and user modeling (§10). Where the documents conflict, this document prevails. 

### 1.1 Design Stance
* **Deployment**: A single-tenant internal enterprise platform. One organization runs it, and its users have different permissions. Cross-tenant isolation is out of scope in this version, but per-user permission boundaries apply throughout.
* **Runtime**: This document specifies the harness as the runtime for the agent loop. Third-party agent runtimes are out of scope in this version, and all model calls are made by the control plane.
* **Autonomy**: Agents operate autonomously inside containment. Human approval is required for irreversible and external-facing actions (§4.3).
* **Standards**: Requirements are stated semantically. Where a widely adopted open standard exists, it is named as the reference (MCP for tool and resource interoperability, container images for environments, OpenTelemetry-compatible exports for traces). Where none exists, this document names no product or format.

### 1.2 Conformance Profiles
Requirements are tagged with the lowest profile at which they become mandatory, and profiles are cumulative: Standard includes every Core requirement, and High-assurance includes every Standard requirement.

| Risk factor of the deployment | Minimum profile |
|---|---|
| Single agent, trusted inputs, no side effects outside the sandbox | Core |
| Side-effecting tools, external or untrusted data, or multiple users with different permissions | Standard |
| T0–T1 self-modification | Standard, plus §6 |
| Research-mode self-modification (§6.12) | High-assurance, with the microVM isolation tier |
| Autonomous or long-running operation (including autonomous open-ended agents and heartbeats), irreversible actions, sensitive data, or T2-or-higher self-modification | High-assurance |
| Multi-agent orchestration | Overlay: the profile is set by the deployment's own risk factors, and the Multi-Agent System PRD applies on top |

* A deployment's profile is the highest profile triggered by any of its risk factors. It must be declared in the deployment's configuration and recorded in the run provenance manifest (§3.6).
* **Tags.** A tag in square brackets follows each requirement's label. For a bold run-in heading that groups bullets, the heading's tag applies to every bullet in the group unless a bullet carries its own tag.
* **Conditional** requirements apply only when the feature they govern is enabled (user memory, proactive behavior, passive observation, computer use). **Post-v1** marks material retained for design continuity that is outside the release trains.
* The modal verbs in a requirement (MUST, SHOULD, MAY) keep their meaning within the tagged profile.
* Appendix C lists every requirement by profile.

## 2. Core Definitions
* **Model**: The learned inference system.
* **Harness**: The control plane machinery driving the model loop, policy, and tool routing.
* **Session**: The durable history/state container for ongoing work.
* **Context**: The active, filtered information supplied to a specific model invocation.
* **Sandbox**: The isolated execution plane where code, API requests, commands, and side effects operate.
* **Tool**: A callable capability exposed to the model via an Agent-Computer Interface (ACI).
* **Subagent**: A separately-scoped agent instance spawned or coordinated by the harness, with its own context, budgets, and tool/credential scope.
* **Event Log**: The append-only, harness-owned record of every model turn, tool call, observation, approval, handoff, and budget event; the authoritative source for audit, replay, and resumption.
* **Trial**: A single execution of an evaluation task. Because model behavior is non-deterministic, results are aggregated over multiple trials.
* **Transcript vs. Outcome**: The *transcript* is the record of how the agent proceeded; the *outcome* is the verifiable final state of the environment.
* **Editable Surface**: The set of harness components (instructions, tool definitions, workflow code, skills, memory, configuration) that an improvement process is permitted to change.
* **Self-Modification**: Any change to the harness's own configuration or code made on the basis of execution feedback, whether by a human-run optimizer, an automated loop, or an agent editing its own instructions or skills.
* **Submission**: A candidate result that an agent presents for scoring. At the moment of submission it is frozen as an immutable snapshot (§5).
* **Evaluator Environment**: The fresh, isolated environment in which a submission is scored, separate from the environment where the agent worked.
* **Conformance Profile**: One of Core, Standard, or High-assurance. A profile is a cumulative set of requirements selected by the deployment's risk factors (§1.2).
* **Effect Class**: A tool's declared side-effect category: read-only, reversible write, irreversible, or external-facing (§4.3).

## 3. Functional Requirements

### 3.1. The Agent Loop & Active Context Management
* **Minimal Loop Execution** [Core]: The harness must continuously assemble active context, invoke the model, route tool calls/approvals, execute in the environment, and record observations until a terminal state is reached.
* **Active Context Selection** [Core]: The harness must treat the active context as an engineered, constrained resource. It must actively select which ingredients (instructions, history, schemas, tool results) enter the prompt, rather than naively appending all historical state.
* **Relevance Filtering (Anti-Bloat)** [Core]: To prevent decision degradation, the harness must proactively exclude irrelevant material that would compete for the model's attention. Exclusion is a decision made by scoring candidate material against the current step (Relevance-Ranked Selection) and fitting it to a budget (Token-Budget Selection), not only a consequence of age or size.
* **Relevance-Ranked Selection** [Core]: Candidates for the active context (slices of durable history, tool results, recalled memories and topics, hits from earlier runs, and retrieved passages) are scored against a query derived from the current step: the latest instruction, the open task, and the working state. Core scoring is lexical (BM25), which suits exact terms, identifiers, and error messages, combined with a recency decay. Scoring is deterministic: the same candidates and query produce the same ranking in every implementation.
* **Hybrid and Reranked Candidate Retrieval** [Standard, conditional]: Where a dense retriever is configured, the lexical and semantic rankings are fused with Reciprocal Rank Fusion, and where a reranker is configured, the fused candidates are reranked by a cross-encoder or an equivalent model before selection, using the same primitives and settings as §8.1. Both are optional components and are versioned control-plane configuration (§3.6); without them, the Core ranking applies. Deployments that have them are expected to use them.
* **Diversity and Deduplication** [Standard]: Before selection, near-duplicate and heavily overlapping candidates are removed by deduplication or Maximal Marginal Relevance (MMR), so that the context carries one copy of an idea rather than several. Each removal is recorded with its reason.
* **Token-Budget Selection** [Core]: Selection fills a token budget for recalled and retrieved material, set as a share of the model's window, and never causes the assembled prompt to exceed the window. The default is a greedy choice by score per token; a knapsack-style optimization is permitted. Ties are broken deterministically, and the selection (what was included and what was excluded, with reasons) is recorded in the Event Log so that it can be audited and replayed.
* **Priority-Based Prompt Assembly** [Core]: Prompt content is assembled by priority class. Protected classes are never dropped to make room: system instructions and tool definitions, the task's instructions and constraints, working state, the most recent turns, and results of calls still pending. Lower classes (recalled history, older tool results, retrieved passages) fill the remaining budget in score order. A small item that is still referenced is protected from age-based clearing, and a large item is replaced by a pointer and a short excerpt. Selection is applied at defined points, so that it does not invalidate the prompt cache on every turn (Cache-Aware Context Assembly).
* **Query-Focused Summarization** [Standard]: Compaction summaries are written for the current task: the summarization request carries the task's goals, constraints, and working state as the query, so that what the task needs is preserved and what it does not is condensed. Summaries remain lossy and are labelled as such (Lossy Transformation Awareness).
* **Progressive Disclosure** [Core]: The harness must avoid monolithic system prompts. It must provide enough baseline information to orient the agent, while keeping deep instructions, documentation, and operational rules discoverable so they are loaded only when a task requires them.
* **Dynamic Skill Loading** [Standard]: The system must support packaging instructions, scripts, and context into reusable "skills" that the agent can retrieve just-in-time, rather than injecting all possible workflows into every session.
* **State Decoupling (Durable vs. Active)** [Core]: The system must strictly decouple the persistent, append-only session log (Durable History) from the specific text window sent to the model (Active Context).
* **Selective Hydration** [Standard]: Persistent availability must not result in automatic prompt inclusion. The harness must retrieve and inject slices of durable history into the active context only when relevant to the current step.
* **Ephemeral Context Exclusion** [Standard]: The harness must support injecting ephemeral state (e.g., current UI state, live tool schemas, temporary runtime metadata) into the active context without committing it permanently to the durable session log.
* **Structured Working State** [Standard]: For long-running tasks, the harness must support externalizing task progress into explicit, structured artifacts (e.g., todo lists, feature status files, plans, or output manifests) rather than relying solely on natural-language history. Agent-maintained notes files (e.g., `NOTES.md`, `MEMORY.md`) are an accepted form of this state; they must be stored durably and versioned, and consolidated by a background job so that they do not themselves become a source of context bloat.
* **Artifact Injection** [Standard]: The harness must be capable of treating structured artifacts as high-signal, stable context. It must ensure the current state of these artifacts is predictably injected into the active prompt, decoupled from standard conversation compaction limits.
* **Compaction Strategy** [Core]: The harness must handle context overflow by summarization or progressive disclosure, used as the backstop in the hybrid strategy below.
* **Hybrid Context Strategy** [Core]: The default strategy is retrieval-first. Durable history stays in the Event Log, working state is externalized into structured artifacts, and slices are hydrated into the active context only when relevant. Compaction is an overflow backstop that triggers at a configurable fraction of the model's context window (for example, 75%), always preserves the raw history, and is batched so that it invalidates the prompt cache as rarely as possible. Compaction reduces the active context and does not delete knowledge: durable facts are kept in the ledger, in topic memory, and in the searchable history of this and earlier runs, independent of the compressed transcript.
* **Lossy Transformation Awareness** [Core]: The harness must treat compaction (summarization) explicitly as a lossy context transformation, recognizing that details deemed irrelevant now may be required by the model later. Compaction must never overwrite or delete the raw durable history. The summary states that it is lossy, names the span it replaces, and tells the model how to recover the original, and a ledger of exact facts is maintained beside it (Exact-Fact Ledger).
* **Retrieval of Compacted State** [Core]: The harness must provide the agent with a mechanism to query and retrieve the original, uncompacted history if the active summary lacks the detail required for a subsequent decision. Retrieval may be direct (the original events) or by consultation (Compacted-History Consultation).
* **Exact-Fact Ledger** [Core]: The harness maintains a separate ledger of exact facts taken from the run's events as they occur, so that it exists before any compaction and survives a failed one, and presents it alongside every compaction summary. Facts are preserved verbatim, never paraphrased: file paths, identifiers (such as run and cluster ids), error codes, and configuration values (such as the model deployment, endpoint, and runtime version) with their provenance. Each entry cites the event it came from and is verified to occur verbatim in that event. The ledger is injected with the summary, is protected from budget-based exclusion, and is bounded in size, with any overflow retrievable on demand. Extraction of these types is deterministic and does not depend on a model.
* **Decision and Constraint Ledger** [Standard]: The ledger also records decisions (the decision taken, its rationale, and the alternatives rejected) and constraints (stated as explicit requirements, for example that the work must run locally or that data cannot leave the device). Each entry cites its source event and a verbatim supporting quote, which the harness verifies; an entry that fails verification is discarded and logged. Constraints stated in the task or by the user are never dropped by compaction.
* **Compacted-History Consultation** [Standard]: When the summary and the ledger lack a detail the agent needs, the agent can consult the original history through a read-only reader that has no tools and runs in an isolated context. The reader is given a named span and a question and returns only the missing information, with evidence that cites events and quotes them verbatim; the harness verifies every citation. The result is untrusted (§4.3), bounded in size, counted in the budgets (§3.3), logged, and limited per run. The harness also tells the agent when its latest action refers to an identifier that is absent from the active context but present in a compacted span. Consultation obeys the return contract of §5 (Subagent Isolation and Return Contract) and is enabled by default only after it has been evaluated against retrieving the raw events directly, for quality and cost (§3.6).
* **Compaction Miss Tracking** [Standard]: The harness records a compaction miss whenever a retrieval or consultation falls inside a compacted span, promotes the exact facts it finds into the ledger, and reports the miss rate and the ledger's coverage of the facts that steps needed (Context and Memory Quality Metrics).
* **Non-Destructive Tool Result Clearing** [Standard]: Stale raw tool outputs deep in the history may be cleared from the active context (replaced by a stub or pointer), but the full result must remain in the durable history and be retrievable on demand.
* **Just-in-Time Retrieval** [Standard]: The harness must support carrying lightweight references (file paths, queries, identifiers) in context and letting the agent pull the underlying data in only when needed, using tools such as `grep`, `head`, or search, rather than preloading data.
* **Cache-Aware Context Assembly** [Standard]: The harness must assemble prompts so that new information is appended after a stable prefix, avoiding mid-prompt edits or reordering that invalidate the model provider's prompt/KV cache. Any relevance-filtering or compaction step must account for the cache-invalidation cost it incurs.
* **Scheduled Wake-Ups (Heartbeats)** [High]: For long-lived background agents, the harness may support scheduled turns in which the agent wakes, evaluates state, and returns to sleep if no action is needed. Heartbeats are off by default, require explicit per-agent enablement with a minimum interval (for example, 30 minutes), and are subject to the same budgets, logging, and approval rules as any other turn.
* **Incremental Context Updates** [Standard]: Agent-maintained context (playbooks, notes, learned guidance) must be updated by itemized deltas (identifier plus description) merged through deterministic logic, with periodic deduplication, rather than by wholesale model rewrites, which cause context collapse and brevity bias.
* **Governed User and Context Memory** [Standard, conditional]: When the harness stores memory about a user or their context (preferences, inferred beliefs, observed behavior), each record must carry its supporting evidence, a confidence value, and a staleness rate. Records revised down to zero confidence stay stored but are hidden from default retrieval. The user must be able to inspect, edit, delete, and add records, and deletions must extend to records derived from the deleted ones. Retention periods are set by organizational policy and must be configurable per memory scope. The evidence, confidence, and staleness fields are the Memory Record Metadata and the decay constant of Retention, Decay, and Eviction.
* **Memory Record Metadata** [Standard]: Every durable memory record carries a stable identifier, its source, creation time, last-access time, confidence, sensitivity, expiry time, and retention policy, in addition to its provenance (§4.3). These fields are the basis on which memory is validated, retrieved, retained, and expired.
* **Deterministic Memory Policy** [Standard]: What may be stored, retained, retrieved, and by whom is decided by a deterministic rule-based policy engine. Authorization and mandatory storage restrictions are never delegated to a model. A model may contribute a supplementary semantic classification, but it can only make a decision stricter (for example, from store to quarantine), never more permissive.
* **Sensitive-Data Detection** [Standard]: Before a record is stored, the harness detects sensitive data (personal data, credentials, and other configured categories). A match is excluded, redacted, or stored with the declared sensitivity and access restrictions, as policy directs, and the decision is logged.
* **Confidence and Provenance Thresholds** [Standard]: Facts extracted by a model are stored only with valid provenance and at or above a configured confidence. Below the threshold they are rejected or held for review, and the outcome is recorded.
* **Contradiction Detection** [Standard]: When a new record conflicts with an existing one, the conflict is detected and flagged for resolution. Neither record silently overwrites the other, and retrieval marks conflicting records until the conflict is resolved.
* **Retention, Decay, and Eviction** [Standard]: Temporary memories expire after their time to live. The priority of older and less-used memories decays exponentially (S(t) = S0 · e^(−λt)), which lowers their retrieval priority without deleting them. Permanent facts and explicitly retained records do not expire merely by age. When storage is constrained, the least recently or least frequently used records are evicted, never records under permanent or explicit retention. Every expiry and eviction is logged.
* **Deduplication and Entity Resolution** [Standard]: Repeated facts are merged and records that refer to the same entity are resolved, preserving the provenance of every merged source.
* **Incremental Topic Memory** [Standard]: Durable facts, decisions, constraints, preferences, and ongoing work are recorded as individual topics as the run progresses, not only in a summary produced when compaction happens or when the run ends. A topic is available to context selection independently of the compressed transcript, carries its source and confidence (Memory Record Metadata), and is written through the memory policy (Deterministic Memory Policy).
* **Cross-Run History Retrieval** [Standard]: The agent can search the history of earlier runs within its permitted scope (by default the same project) and read the cited original, so that a fact missing from the active context can be recovered from the run it came from while that history exists. Hits cite the run and the event and are untrusted observations (§4.3); permissions are enforced in the retrieval layer at query time (§8.3) and results are not cached across permission boundaries (§3.8). When a run's raw history has expired, only the ledger entries and topics that policy retained remain, and deleting a run deletes the entries derived from it.
* **Project-Scoped Memory** [Standard]: Memory has scopes (run, project, user, and organization). Project memory is shared by the runs of one project and isolated from every other project, and the isolation is enforced by the deterministic policy, not by instructing the model. A run's topics start at run scope and reach project scope only by promotion, which is a write at the target scope that passes the whole memory pipeline. Retention, enablement, and sensitivity limits are configurable per project. Project knowledge documents are retrieved through §8. Whether a run belongs to a project is never inferred: when project memory is enabled, the user is asked whether the work is part of a project and which one, and the answer, including "none", is recorded with the run.

### 3.2. Tool Design & Agent-Computer Interface (ACI)
The harness must treat the Agent-Computer Interface as an experimental variable distinct from human-facing APIs.

#### General ACI Requirements
* **Model-Usable Exposure** [Core]: Capabilities must be exposed in forms designed for reliable LLM use (e.g., providing a structured `update_record` instead of a raw `database_shell`).
* **Mistake-Proofing (Poka-yoke)** [Core]: Tool interfaces must be designed so that common mistakes are structurally impossible or rejected with an actionable error (e.g., requiring absolute file paths, enumerated values, and bounded ranges).
* **Format Economy** [Standard]: Where machine validation is not required, tool inputs and results should favor naturally occurring text structures (e.g., Markdown or plain text) over deeply nested or heavily escaped JSON. Where strict validation is required, a schema must be used. The representation is chosen by consumer: results shown to the model favor natural text, and results that machines validate use a concise schema (Format Optimization).
* **Format Optimization** [Standard]: Beyond truncation, results are shaped to the downstream need before they enter the context: only the fields the next step needs, aggregates with counts and exceptions for large result sets, pagination with continuation cursors, deduplication of repeated content, and references to artifacts stored outside the context. A result that was truncated, summarized, or paginated says so explicitly and is never presented as complete, and critical identifiers, errors, provenance, and required records are preserved or reliably retrievable. Verbosity adapts to the consumer. Token savings and information loss are measured against a full-result baseline.
* **Selection Cost Management (C_selection)** [Standard]: Tool count is not a monotonic measure of capability. The harness must avoid bloated or overlapping toolsets (e.g., exposing `search`, `find`, and `query` simultaneously). Tools must be distinct, and if many exist, they should use namespacing to reduce the model's decision burden. Selection errors are classified by type (wrong tool, missed tool, invalid call, unnecessary call, unsafe selection) and attributed to task, model, selector version, and tool, and the cost of selection (tokens, search latency, and retries) is attributed to the task. Dynamic exposure is a cost optimization and not a security boundary: authorization is enforced independently when the tool executes (§4.3).
* **Selection Error Alerting** [Standard]: The harness raises an alert when the tool-selection error rate or the cost of selection exceeds a configured threshold over a rolling window with a minimum sample size, with severity levels and de-duplication. An unauthorized or prohibited tool selection that reaches execution raises an immediate alert regardless of the aggregate rate. Alerts carry enough context to diagnose the failure without exposing sensitive payloads. Selection is evaluated against a labeled benchmark of representative tasks, and a change to ranking or exposure logic is regression-tested. If discovery or selection fails, the harness retries discovery or asks for clarification and blocks unsafe execution.
* **Tool Exposure Policy** [Standard]: Each agent receives a per-agent allowlist of tools. When a catalog is large, tools beyond a small always-loaded set are loaded on demand through search over namespaced tool descriptions. There is no hard cap on tool count. The tool-selection error rate is measured, and exceeding a configured threshold triggers namespacing or dynamic loading.
* **Tool-Specific Retry Policies & Idempotency** [Standard]: Automatic retry must not be treated as a universal recovery strategy. The harness must explicitly distinguish between idempotent tools (safe to retry, e.g., `set_status`) and non-idempotent tools (dangerous to retry, e.g., `charge_card` or `send_email`). Retries on non-idempotent side effects must be gated by explicit safeguards such as idempotency keys, deduplication records, or read-before-retry checks. Every tool must declare its idempotency class at registration (idempotent, non-idempotent with an idempotency key, or non-idempotent without one). A tool that does not declare it is treated as non-retryable.

#### Four-Property Tool Design
Every tool exposed to the agent must be deliberately engineered according to four properties, recognizing that tool definitions and results are injected directly into the model's text context as prompts:
* **Affordance (Capability Scoping)** [Standard]: The harness must expose narrow, task-aligned capabilities rather than overly broad interfaces (e.g., a targeted `book_flight` rather than a generic `http_post`).
* **Contract (Input Schema & Descriptions)** [Core]: Tool names, descriptions, and input schemas must be concise and unambiguous to minimize the context burden. They must not force the model to guess complex formatting or choose between vaguely described options. Where ambiguity remains, descriptions should include short examples and explicit boundaries stating what the tool does not do.
* **Observation (High-Signal Context)** [Core]: Tool results must be treated as context engineering. Because returned data consumes the model's limited context window, the harness must filter out irrelevant API payloads and metadata before inserting results. If results are large, the harness must truncate them and provide mechanisms to retrieve more. Result size caps are configurable per tool, and every truncated result carries a handle for retrieving more.
* **Feedback (Model-Usable Errors)** [Core]: Tool errors are observations. Failures must not crash the run or return opaque strings; they must return structured, actionable error states (e.g., "Branch not found; available: [main, dev]") so the model can intelligently recover. Every error carries a category aligned to the failure taxonomy in §3.7, a retryable flag, an actionable hint, and valid alternatives where they exist.

### 3.3. Budgets, Stopping Conditions & Verification
* **Multi-Vector Budgeting** [Core]: The harness must enforce a comprehensive vector of resource budgets to limit autonomy, explicitly including: maximum turns ($B_{turns}$), tokens consumed ($B_{tokens}$), wall-clock time ($B_{time}$), financial cost ($B_{cost}$), tool invocations ($B_{tools}$), and concurrent workers ($B_{concurrency}$). Core requires budgets for turns, tokens, and time. Standard adds cost and tool invocations. High-assurance adds concurrency, compute, and submissions. All budgets are enforced by one central budget service that every model call, tool invocation, and submission passes through, and agents do not keep independent budgets. Concurrency limits simultaneous operations and is distinct from the cumulative budgets.
* **Unmetered Resource Safeguards** [Core]: A budget dimension that the platform does not meter (for example compute) is declared unmetered in the run's manifest, and a missing measurement is never treated as zero consumption. Independent safeguards bound the risk: iteration and wall-clock limits, a bounded worker pool and bounded queues, per-process CPU-time and memory limits, quotas for submitted jobs, and workflow-scoped cancellation and cleanup of orphaned processes and external jobs.
* **Budget Reservation and Reconciliation** [Standard]: Before a model call or tool call whose cost is uncertain, the budget service atomically reserves its worst-case tokens and cost, so that concurrent callers cannot reserve the same remainder. After the call it reconciles the reservation to the provider-reported usage, and it releases the reservation if the call did not run. A call whose usage is unknown (for example after a timeout) is charged at its reserved estimate and flagged until reconciled, and is never treated as free. Retries and failed calls consume budget, and a submission is counted before the external job is launched.
* **Hierarchical Budgets** [Standard, conditional]: Where work is delegated, a global budget is shared by the whole workflow and each agent or task may receive a local allocation bounded by it, so that the total consumption of all agents can never exceed the global budget.
* **Bounded Looping** [Core]: The system must use budgets to convert unbounded "keep trying" instructions into strict operational policies, ensuring no agent process can run indefinitely.
* **Budget Enforcement Mode** [Core]: Budgets are enforced as hard stops. The harness warns the agent through ephemeral context when a budget reaches a configurable fraction of its limit (80% by default) so that it can wrap up cleanly, and it records which budget caused any termination.
* **Stuck-Loop Detection** [Core]: The harness must monitor the action stream. When the agent repeats the same action with the same result a configurable number of times (e.g., 4), the harness injects corrective guidance once through ephemeral context. If the repetition continues, the harness terminates the run, and in High-assurance deployments it escalates to a human instead. This is recorded as a distinct termination reason (Architectural error, per §3.7), not a generic failure.
* **Compute, Submission, and Evaluator Budgets** [High]: For workloads that use accelerators or iterative scoring, the budget vector must also include compute ($B_{compute}$, e.g., accelerator-hours across all environments, including child sandboxes) and the number of scored submissions ($B_{submissions}$). Evaluator spend (model calls and compute used by the evaluator) must be metered separately from the agent's budgets so that neither hides the other.
* **Completion vs. Termination** [Core]: The system must explicitly distinguish between task *completion* (verifiable success) and run *termination* (forced stops). The harness must not collapse these states into a generic "done" and must accurately report which specific budget or constraint caused a termination.
* **External Stopping Control** [Core]: The harness must govern the stopping condition of the loop. While the model may output a stop sequence or propose a final answer, the harness must independently evaluate termination triggers (e.g., budget exhaustion, guardrail blocks, fatal tool errors, or human intervention) and verification triggers before accepting the stop.
* **Evidence-Based Completion** [Core]: The harness must not accept the model's conversational claims of success (e.g., "The bug is fixed" or "The task is complete") as proof of completion. 
* **Observable Verification** [Core]: Task completion must be tied to observable, external state outside of the model's own assertions. The harness must support executing objective verification checks (e.g., running regression tests, querying database state changes, or validating API payloads) before marking a task as resolved.
* **Mechanisms Over Prose (Deterministic Enforcement)** [Core]: The architecture must prioritize code-based mechanisms over prompt-based prose instructions for enforceable rules. If an architectural rule is objective and mechanically checkable (e.g., forbidding specific imports, schema validity, or file path boundaries), it must be enforced by the harness, sandbox, or linters. The system must change the failure mode from relying on model obedience to mechanically rejecting invalid state.
* **Scope of Model Judgment** [Core]: The harness must rely on the model's judgment only for decisions that genuinely require semantic interpretation (e.g., evaluating relevance, determining task strategy, or interpreting ambiguous intent). The model must not be burdened with remembering rules that the system can cheaply and perfectly enforce.
* **Safety Over Task Completion** [Core]: Guardrail blocks, safety bounds, and approval requirements take strict precedence over task success. No completion pressure, budget pressure, or model-proposed justification may cause the harness to relax them.
* **Legible Failure and Deterministic Paths** [Core]: Where a deterministic code path can accomplish a step, it must be preferred over model judgment. When the agent cannot proceed, the harness must fail with an explicit, actionable error rather than allowing the model to fabricate a result.
* **Initiative and Interruption Policy** [High, conditional]: A harness that lets an agent act or surface suggestions without being asked must apply an explicit policy and must rate-limit proactive actions. For each candidate action the policy weighs the probability that it is useful, its benefit, and the costs of a false positive and of a false negative, and it acts or interrupts only when the expected utility of doing so exceeds that of staying silent. A token-bucket rate limit caps how many suggestions surface per period, because the utility of one suggestion depends on how many others are shown. Rule-based thresholds are the fallback when estimates are unavailable. The policy applies only when proactive features are enabled. Proactive actions may execute autonomously only when they have no irreversible side effects; all others go through approvals (§4.3). Any claim that a proactive action was performed must be backed by tool evidence.
* **Confidence-Gated Action** [High, conditional]: When a prediction or inference triggers an action, its confidence must be exposed and calibrated against observed outcomes, and the action must be gated on it. Confidence may be elicited from the model as a conservative verbalized score or computed from agreement among sampled predictions. Underconfidence is preferable to overconfidence when acting on inferred user preferences.

### 3.4. Multi-Role Evaluation & Feedback Loops
* **Separation of Generation and Evaluation** [Core]: For subjective outputs that cannot be deterministically verified (e.g., prose quality, architecture design, or policy interpretation), the harness must support separating the roles of Generator and Evaluator. The system must not rely on a single model call to blindly grade its own subjective output.
* **Evaluator Fallibility** [Core]: The architecture must treat model-based evaluators as fallible components. Where objective, deterministic checks exist, they must always take precedence over LLM-based grading. Model-based evaluators must be calibrated against a human-graded sample and, where feasible, should differ from the generator in model and context to limit self-preference bias. An evaluator is approved for a defined use only when it meets pre-registered thresholds (Evaluator Approval and Abstention).
* **Evaluator Approval and Abstention** [Standard]: Every evaluator, whether code, model-based, or human, is treated as a fallible decision component. Verdicts are structured per criterion with reason codes and evidence references, and an evaluator may return PASS, FAIL, PARTIAL, or UNCERTAIN. An evaluator is approved for a defined use case only when its measured performance on a held-out, independently adjudicated validation set meets overall and category-level thresholds registered before the evaluation, judged on confidence intervals and against risk-specific false-acceptance limits; otherwise it is advisory only or requires additional independent verification. Hard constraints, authorization rules, schemas, and objective invariants take precedence over any semantic score, and a high score alone never authorizes a consequential action. When an evaluator is uncertain, outside its validated scope, inconsistent, or suspected of drift, the system abstains, invokes an approved independent check, or escalates to a human, and an unresolved high-risk case does not proceed automatically. Retries, extra evaluators, and escalations count against the budgets (§3.3). False-acceptance and false-rejection rates, calibration, drift, and overrides are monitored, and a change of evaluator, model, or rubric is regression-tested.
* **Evaluator Independence Levels** [Core]: An evaluator that reuses the agent under test, or the same model, has low independence and must be labeled as such in the results. It ranks below deterministic checks and below evaluators that use an independent model, context, and credential. In Core deployments, labeling is sufficient. In Standard deployments, any evaluation that gates a promotion, a release, or a claim must use an independent model, context, and credential. In High-assurance deployments, every material claim must additionally be backed by a deterministic or independent check.
* **Judge Bias Controls** [Standard]: A pairwise comparison by a model-based judge must be run twice with the order swapped and the scores aggregated. Judge prompts should penalize unnecessary length, and the judge model should differ from the model that produced the outputs. The calibration required under Evaluator Fallibility must be completed before the judge gates anything.
* **Trajectory Access for Evaluators** [Standard]: Evaluators may be given the agent's trajectory up to the point of evaluation, mounted read-only and written by the harness outside the agent's reach, so that tampering, test overfitting, and reward hacking can be detected. That content is untrusted input (§4.3).
* **External Evidence Loops** [Core]: The harness must engineer strong feedback loops by making ground truth queryable. When an agent executes a state-changing action, the harness must expose the external consequences of that action back to the agent (e.g., by providing access to compiler output, application logs, browser state, database contents, or API responses) so the agent can observe and revise its work.
* **Agent Legibility** [Core]: The architecture must ensure the execution environment is highly legible to the agent. Hidden human assumptions (tribal knowledge) must be pushed into inspectable artifacts. The harness must provide tools for the agent to discover environmental rules independently (e.g., discoverable database schemas, explicit test entry points, searchable logs, structured documentation, and deterministic application launch states).

### 3.5. Interoperability & Protocol Management (e.g., MCP)
* **Protocol Boundary** [Core]: The harness must treat capability protocols like the Model Context Protocol (MCP) strictly as interoperability interfaces for accessing external tools, resources, and prompts. The protocol must not be relied upon to govern the agent architecture itself.
* **Control Plane Ownership** [Core]: Even when integrating with standardized external servers, the harness must retain exclusive ownership of the agent loop, context compaction, retry policies, human approvals, and sandbox provisioning. It also owns the definitions an execution uses (Definition Pinning).
* **Definition Pinning** [Core]: Every execution is pinned to a manifest that lists each definition it uses (workflow, prompts, tool schemas, evaluator rubrics, and budget and isolation-tier policies) with its identifier, immutable version, and content hash. Published versions are immutable, the control plane alone publishes and assigns versions, and runtime agents may propose changes but cannot make them authoritative. Components resolve definitions only through the manifest, never through an implicit latest version, and verify the hash before use. A missing or mismatched definition fails closed with a controlled error and is never replaced by another version. A new version affects new executions unless an explicit, audited migration says otherwise, and the manifest and the definitions it references are retained for the audit period. Pinning identifies what an execution used; it does not make a model's output deterministic.
* **State Decoupling** [Core]: The harness must distinguish between protocol-level execution state (e.g., a successful JSON-RPC transport response) and semantic task state (e.g., the tool successfully executed its side effect vs. returning a logical failure).
* **Client-Host-Server Architecture** [Standard]: For MCP, the harness acts as the host, managing one client per connected server. Servers expose **Tools**, **Resources**, and **Prompts**, and every such primitive is mediated by the harness.
* **Server Trust** [Standard]: Tool descriptions, resource contents, and prompts supplied by MCP servers are untrusted external data (see §4.3) and are subject to the same provenance tracking, containment, and approval gating as any other external input. Agents may use only servers from an organization-approved registry. Each server's tool definitions are pinned by hash at approval, and any change to a definition requires re-approval before it takes effect. Local servers run inside a sandbox.

### 3.6. Configuration & Harness Evaluation
* **Harness as a Behavioral Component** [Core]: The system must treat the harness configuration itself (e.g., prompt construction, reasoning defaults, context retention policies, and tool interfaces) as a core driver of agent capability. The architecture must account for the fact that harness changes can alter or degrade observed agent quality even when the underlying LLM remains completely unchanged.
* **Configuration Versioning** [Core]: All control-plane policies, including system instructions, context-clearing logic, and tool definitions, must be strictly versioned as production code.
* **Agent vs. Evaluation Harness Separation** [Standard]: The architecture must explicitly separate the *Agent Harness* (which runs the loops and tools in production) from the *Evaluation Harness* (the testing infrastructure that provisions stable environments, records trials, and grades outcomes). 
* **Holistic Performance Measurement** [Standard]: The evaluation infrastructure must recognize that a benchmark score measures the entire system: `performance = F(model, harness, environment, task, grader)`. Therefore, any adjustments to the agent harness or sandbox environment must be tested against representative evaluation benchmarks to prevent unintended regressions like system forgetfulness or reasoning drops.
* **Assumption Expiration & Scaffolding Pruning** [Standard]: The architecture must treat every piece of harness scaffolding (e.g., context-clearing workarounds, subagent loops, strict prompt templates) as a hypothesis about a *current* model limitation. When the underlying model is upgraded, these assumptions must be re-tested. The system lifecycle must include pruning obsolete scaffolding that has become "dead weight" to prevent accumulating unnecessary latency, token costs, and complexity.
* **Optimizer-Produced Artifacts Are Versioned Config** [Standard]: Prompts, few-shot demonstrations, tool schemas, routing/transition definitions, and retrieval parameters produced by automated optimizers (e.g., DSPy or GEPA-style compilers) must be stored as versioned control-plane configuration with provenance (optimizer, input data, metric, parent version) and must not be edited outside the version record.
* **Gated Change Promotion** [Standard]: Any change to control-plane configuration, whether human-authored or optimizer-proposed (including rewritten tool schemas, newly synthesized tools, routing changes, and retrieval retuning), must pass the regression evaluation suite and, according to its risk class, human approval before reaching production. Every promoted change must be reversible by rollback to the prior version. Requirements specific to changes made by self-modifying processes are in §6.
* **Trials and Aggregation** [Standard]: The evaluation harness must run multiple trials per task and report aggregate results with a measure of variance, since single runs are not reliable evidence under non-determinism.
* **Transcript and Outcome Evaluation** [Core]: The evaluation harness must record the transcript separately from the outcome. The outcome must be graded programmatically against environment state wherever possible, and the trajectory (efficiency, safety, logical soundness) must be assessed in addition to the final result. Success is defined by criteria fixed before execution (Outcome Contract and Verdicts), never by the agent's own claim.
* **Outcome Contract and Verdicts** [Core]: Each task has a machine-readable outcome contract fixed before execution: its mandatory acceptance criteria, how each is verified, the success policy, and what to do when evidence is inconclusive. Verdicts are SUCCESS (every mandatory criterion has verified evidence), FAILURE (at least one mandatory criterion demonstrably failed), PARTIAL (some passed but the goal was not achieved), or INCONCLUSIVE (evidence is missing, stale, conflicting, or insufficient). Missing or conflicting evidence cannot produce SUCCESS, and an agent's statement that it succeeded is not evidence. External actions are verified against the authoritative state of the target system where feasible, and a timeout after an external action is checked against that state before any retry. Outcome metrics (success, partial, failure, and inconclusive rates, and verification coverage) are reported by task category and risk with an explicit denominator policy, and evaluation errors are measured by independent audit.
* **Capability and Regression Suites** [Standard]: Evaluations must be split into capability suites (pushing the frontier, low expected pass rate) and regression suites (near-100% expected pass rate, integrated into CI/CD). Capability tasks that are consistently solved must graduate into the regression suite, and saturated tasks must be pruned or replaced with harder ones. Each suite must declare explicit graduation and pruning criteria and record every graduation or pruning decision.
* **Cost-Aware CI** [Standard]: A representative reduced subset of the evaluation suite runs on every change, provided the subset is validated against the full suite. The full suite runs on a defined schedule and before any promotion.
* **Deterministic Testing and Mocks** [Standard]: The evaluation infrastructure must support mocked model responses and simulated human-approval inputs so that routing, approval, budget, and retry logic can be verified deterministically before deployment.
* **Action-Level Security and Privacy Evaluation** [High]: Security and privacy properties must be measured by red-teaming the agent over simulated edge-case trajectories and inspecting the actual tool executions, rather than relying only on question-answering probes about intended behavior.
* **Declarative Task Package** [Standard]: Each evaluation task must be defined as a declarative package containing the instruction, the environment definition, the tests or grader, and the configuration (scoring direction, limits, test visibility), and must be validated before any run starts. This document names no package format; a widely adopted standard should be used if one exists at implementation time.
* **Fresh Evaluator Environment** [Standard]: Each submission must be scored in a fresh, isolated environment built from a clean image, never in the environment where the agent worked. This makes scoring reproducible and rules out state carry-over and tampering.
* **Declared Test Visibility** [Core]: A task must declare whether its tests are hidden from the agent or public (mounted read-only in the agent's environment). Tests are hidden by default. Public tests are development aids and cannot support a held-out or generalization claim. The declaration is part of the pinned manifest, the declared policy and the actual runtime state (whether tests are mounted) are recorded separately, the tests and expected results that were exposed to the agent are recorded, and an invalid or contradictory declaration is rejected. A generalization claim requires a separate evaluation on data the agent was not exposed to.
* **Run Provenance Manifest** [Core]: Every run must record the identifiers and versions of the model, harness, agent software, environment, task, and grader, together with the context-window and output-token limits, so that results are reproducible and comparable. This operationalizes performance = F(model, harness, environment, task, grader). It also records the deployment's declared conformance profile (§1.2). The manifest is a versioned, integrity-protected record that also pins the definitions used (§3.5), the input, dataset, and retrieval-index versions, the termination status and outcome verdict with evidence references, and usage and cost; child agents and model calls link to their parent run. A value that is unavailable is recorded as unavailable and never invented, and recorded, unavailable, and not-applicable fields are distinguished.
* **Bounded Submission Loops** [Standard]: Where an agent may submit repeatedly and receive feedback, each submission is an atomic snapshot (§5), the number of scored submissions is bounded by $B_{submissions}$ (§3.3), and the feedback returned to the agent must be limited in granularity, because every scored submission leaks information about the hidden tests.
* **Confirmatory Final Evaluation** [Standard]: Confirmation is mandatory when a result is selected from two or more scored submissions, and for any promotion or release gate. When a final submission is chosen by a declared rule (e.g., the best primary score in a stated direction) from several scored submissions, its reported result must be confirmed by an evaluation on data, seeds, or instances that were never used for feedback or selection, and the number of submissions used must be reported. The unconfirmed score is an upper bound, not a result.
* **Replication and Variance** [Standard]: Where evaluation is stochastic or expensive, each task must declare a replication policy derived from a pilot measurement of variance, with a floor of 3 trials, and results must report variance (for example, a confidence interval). Selecting the best of several results on a noisy signal requires a confirmatory repeat.

### 3.7. Dual-Audience Observability & Failure Classification
* **Human Operator Telemetry** [Core]: The system must provide observability data tailored for human engineers to debug the harness itself. This includes tracking model turns, tool failures, latency, token consumption, cost budgets, retries, and approval events. The minimum interface is the command line: the operator identifies a run and inspects its status, model and version, tool-call events, errors and termination reason, token and cost usage, and recorded interventions, and a category the harness does not collect is reported as unavailable and not assumed absent. Automated collection services, dashboards, and background monitoring are optional and not required; where provided, dashboards show metadata by default. Access to prompt and tool-result content is gated by role, and every access is logged.
* **Agent-Facing Observability** [Standard]: The architecture must treat the agent as a primary consumer of observability data. The agent obtains application-level telemetry (e.g., application logs, compiler traces, system metrics, test results, and browser state) by pulling it through tools, filtered for relevance and labeled untrusted, rather than by having it pushed into context. This gives the agent the evidence needed to verify its own work.
* **Failure Classification Taxonomy** [Core]: The harness must not collapse errors into a generic "task failed" state. It must make failures explicitly observable and classifiable across a precise taxonomy, distinguishing between: Tool errors (selection, contract, or noisy observations), State errors (context compaction loss or lost progress tracking), Environment errors (sandbox mismatches), Architectural errors (faulty recovery, subagent coordination conflicts, or budget exhaustion), and Security/Content errors (provenance/prompt-injections or skill-induced efficiency regressions). Every failed or terminated run receives one primary failure class and optional secondary tags, assigned by the harness and open to human override. The taxonomy is versioned.
* **Trace Completeness** [Core]: Every model turn, the assembled prompt (including the version of any compiled instructions), tool call, tool result, approval event, and budget state must be recorded and linkable in the Event Log, which is the authoritative record. Exports to observability tooling are derived from the Event Log in an OpenTelemetry-compatible form and are never the system of record.
* **Minimum Operator Metrics** [Core]: Operator dashboards must at least report turns, tool failures, latency, tokens, cost, retries, approval events, budget terminations, stuck-loop terminations, and evaluation-integrity events. Retention is set by organizational policy.
* **Context and Memory Quality Metrics** [Standard]: The harness reports context-selection quality (Recall@K and nDCG@K against labelled sets of the items each step needed, and the rate at which excluded items were later re-fetched), compaction quality (the compaction miss rate and the share of labelled exact facts that the ledger preserved) and memory-governance quality (policy-violation rate, false-rejection rate, stale-memory rate, and unauthorized-access rate). Metrics are reported per configuration version, so that a change of selection or memory policy can be evaluated through the gate (§6.3).
* **Correlation Identifiers** [Standard]: Runs, sessions, subagent spans, and handoffs must carry correlation identifiers so that a complete trace can be reconstructed across subagents and orchestration layers.
* **Privacy-Preserving Export** [Standard]: Logs exported for analytics, evaluation, or synthetic-data generation must pass PII redaction and contextual masking of quasi-identifiers (for example, generalizing highly specific details), because basic PII removal is insufficient against agents that can cross-reference behavioral clues at scale.
* **Taxonomy Extensibility** [Standard]: The failure taxonomy must be extensible so that companion specifications (e.g., multi-agent orchestration) can register additional failure classes without redefining the base classes.
* **Self-Modification Errors** [Standard]: The taxonomy must include classes for invalid proposals, regressions after promotion, benchmark overfitting or failure to transfer, reward hacking, diversity collapse in search, implementation drift under execution pressure, over-optimism on noisy results, and harness activation or adherence failures (the target model not loading or not following an updated harness).
* **Evaluation-Integrity Errors** [Standard]: The taxonomy must include classes for evaluator tampering by the code under evaluation, state carry-over between evaluations, leaked or over-granular feedback, selection bias or adaptive overfitting to the scorer, budget or clock reset after recovery, and stale grants left behind after a run (network rules, credentials, sandboxes).
* **Evaluation-Integrity Closure** [Standard]: Evaluation-integrity findings are tracked and resolved at the level of the individual detector, and the status of an integrity class is derived from the states of all the detectors it requires. A class is not closed while any required detector is failing, open, not run, or awaiting verification. Remediation is verified independently, by someone other than the person who made the fix, using recorded evidence tied to the detector's version and to an evaluation run. A waiver is explicit, approved by someone other than the owner, time-bounded, and auditable, and it never counts as a pass. Detector-level findings and the history of closure are preserved after the class is closed.

### 3.8. Middleware & Model Gateway Hooks
* **Hook Layer** [Standard]: The harness must provide an extensible middleware layer between the agent loop and the model provider API, with pre-request and post-response hooks, so that cross-cutting behavior can be added without modifying agent logic.
* **Required Capabilities** [Standard]: Hooks must support injecting context variables, semantic caching, safety and policy screening before a prompt reaches the model and after a response returns, instrumentation, budget accounting, and model routing.
* **Ordering, Observability, and Fail-Closed Behavior** [Standard]: Middleware must execute in a defined, versioned order, and each hook invocation must appear in the trace. Safety and policy hooks must fail closed.
* **Cache Safety** [Standard]: Semantic caching is scoped to the requesting user's permissions and must never return results across trust, tenant, or permission boundaries. It must not be applied to state-dependent queries or to non-idempotent actions, and it is off by default in Standard and High-assurance deployments.
* **Gateway Routing** [Standard]: Routing of sub-tasks across models (by cost, difficulty, or compute budget) is implemented through these hooks. The routing policy is versioned configuration and its spend counts against $B_{cost}$.

### 3.9. Component Composability
Source: Shi, Zhang, and Cui, *A Programming Paradigm for Spatiotemporal Composability* (arXiv:2608.25512). The harness is assembled from components (tools, skills, programs, middleware, adapters, backends, interceptors, and sub-agent configurations) that are added and removed while it runs, including by the self-improvement loop (§6). Two properties are required. **Temporal composability** means that removing a component fully reverses what it did. **Spatial composability** means that components declare what they depend on and that the harness coordinates their activation as dependencies appear and disappear. A *component* is the unit with a dependency declaration, a provision, and an effect function, and an instance of a component is a *fiber*.
* **Revertible Effects** [Standard]: Every change a component makes to harness-owned state (registrations, grants, timers, sandboxes, sessions, subscriptions, interceptors, and workspace state) is made through its context and yields an inverse that the runtime holds. Removing the component runs those inverses in reverse order, so the state returns to what it was before the component was added.
* **Effect Locality** [Standard]: A component creates and disposes each effect in one place, so that cleanup does not depend on a separate uninstall path that its author must remember to write.
* **Stated Equivalence** [Standard]: Reverting restores state only up to an equivalence, for example a restored workspace matches by content and mode but not by inode or modification time. The harness states the equivalence for each resource class and tests against it.
* **Declared Dependencies** [Standard]: Each component declares the keys it requires and the keys it provides, with version ranges. Provisions are disjoint unless isolated, keys are namespaced, and a dependency cycle is rejected when components are registered.
* **Reactive Activation** [Standard]: Each change to the set of provisions is classified, against every component's declared requirements, as activating, deactivating, or neutral. A component activates when its requirements are satisfied and deactivates when one is withdrawn, without an error and without a restart. A binding is withdrawn only after the deactivations it causes have finished, and a binding that an activation reads does not move while it runs.
* **Confinement** [Standard]: A component reads and writes only the keys it declared. An undeclared access is refused and recorded, and the declared set is reviewed when the component is loaded.
* **Isolation and Interception** [Standard]: The same key can resolve differently for different contexts, and cross-cutting behavior (policy checks, logging, rate limits) can be installed on a key at runtime without reloading components or changing the dependency graph.
* **Lifecycle Orchestration** [Standard]: The orchestrator only requests that an instance exist or retire. Lifecycle rules activate and deactivate instances, and an instance is removed only after it is inactive and has reverted its effects.
* **Declarative Reconciliation** [Standard]: The desired set of components is a declarative configuration, and a reconciler turns changes to it into insert, retire, and update operations keyed by stable identifiers.
* **Live Replacement** [High, conditional]: A component can be replaced without restarting the process by retiring its instance and inserting a new one. A replacement applies to a run only if that run opted in to following live changes, and other runs keep their pinned configuration.
* **Compensation for External Effects** [Standard]: An effect that leaves the system boundary cannot be inverted, so it is either withheld until it is approved and committed or accompanied by a declared compensating action. Compensations run in reverse order, and a failed compensation escalates to a human.
* **Independence Check Before Out-of-Order Revert** [Standard]: Reverting a change while later changes remain in place requires evidence that they are independent (disjoint keys and no dependency between them). Otherwise the later changes are reverted first or the result is re-gated.
* **Composability Verification** [Standard]: The lifecycle rules have a machine-checked model within stated bounds, and property-based tests run random interleavings of insert, retire, provide, withdraw, and revert against every implementation.

## 4. Execution Environments, Security & Containment

### 4.1. Execution Environments & The Sandbox
* **Explicit Environment Provisioning** [Core]: The architecture must explicitly define and provision the execution environment, specifying available packages, network egress rules, and resource limits, as these boundaries dictate both capability and failure modes. Provisioning is a verified lifecycle and not an assumption (Verified Environment Provisioning).
* **Verified Environment Provisioning** [Core]: An environment is ready only after the harness has verified that what is running matches what was requested: the resolved image (by digest where the runtime supports it), each mount (source, destination, access mode, availability, and permissions), the network policy, and the resource limits. A runtime-created event or a successful API response is not proof. The agent workload does not start in an unverified environment, a mismatch produces a structured failure with the expected and observed configuration, a missing or mismatched mount is never replaced silently by a different or writable one, and failed resources are cleaned up or quarantined. Requested and observed configuration are recorded separately in the Event Log.
* **Untrusted Execution (Code on Demand)** [Core]: Arbitrary model-generated code must execute strictly within an isolated sandbox. This environment must rely on hard OS/container-level boundaries (containment) to prevent unauthorized file or network access.
* **Isolation Tiers** [Core]: Core requires a hardened container (non-root, restricted system calls, read-only root filesystem, and no host runtime socket). Standard requires stronger isolation for untrusted code, such as a user-space kernel or a microVM. High-assurance requires a microVM for evaluators and for self-modifying runs. The requirement is the isolation property, and named technologies are examples.
* **Isolation Tier Enforcement** [Core]: The isolation tier of an execution is chosen explicitly and enforced by the control plane, not requested by the agent. Tier definitions are versioned and owned by the control plane, and only enabled, implemented tiers can be provisioned. The caller's authorization is checked before provisioning, with identity taken from a trusted authentication mechanism, and an unknown, disabled, or unauthorized tier is denied and never silently replaced by a weaker one. The effective runtime controls are verified against the selected tier before the workload starts, and a mismatch blocks execution. A change of tier during a run needs a new authorization and provisioning decision, a change to the tier policy after the run starts does not alter that run unless explicitly migrated, and the audit record keeps the requested tier, the resolved policy version, the decision, and the observed configuration.
* **Trusted Execution (Predefined Tools)** [Core]: Predefined tools (human-written APIs) must execute in a trusted context (e.g., the Harness or an external MCP server). They must act as controlled proxies, restricted by their explicit API contracts rather than sandbox limits.
* **Persistent Execution State** [Standard]: For tasks that depend on shell or environment state, the sandbox must offer a persistent session (e.g., a persistent terminal session) so that environment variables, working directory, and virtual environments carry across tool calls within a session. Persistent state must be either reconstructible after resumption (§5) or explicitly reported as lost. Across a restart of the harness, the session is restored from durable storage and resumed only after validation and reconciliation (Safe Session Resume).
* **Evaluator Integrity Against Candidate Code** [Standard]: When an evaluator executes the code under evaluation, that code must run as a separate, unprivileged identity, or under equivalent kernel-enforced confinement, that cannot read or modify the evaluator, the tests, the scoring code, or the results. The candidate must not be able to cause the evaluator to switch identities. Hidden tests must not be reachable from the agent's working environment.
* **Backend Parity of Isolation** [High]: The isolation guarantees in this section must hold equivalently on every execution backend (local container, remote virtual machine, cluster scheduler). Where different mechanisms provide the same guarantee on different backends, every backend must pass a common isolation conformance suite before it is enabled and after any change that touches isolation, and a failure blocks the backend from use.
* **Brokered Child Sandboxes** [High]: An agent or evaluator that needs a nested execution environment must request it from a control-plane broker, which enforces policy (allowed images, resource limits, network rules, lifetime, and count). The host container runtime's control socket must never be exposed to an untrusted environment, and children inherit no credentials by default. Child sandboxes count toward $B_{concurrency}$ and $B_{compute}$. The broker provisions children locally by default. Remote backends are disallowed unless the deployment approves them and sets a data-classification rule for what may run there, and a remote backend is a separate trust boundary governed by §4.3.

### 4.2. Separation of Planes & Credentials
* **Orchestrator vs. Isolation Boundary** [Core]: The Sandbox must act strictly as an isolation boundary (controlling reachability, network, and file access), not the orchestrator. The control plane (Harness)—which governs context, tool selection, loop logic, and approvals—must run completely outside the untrusted execution environment to protect policies and audit logs from tampering.
* **Zero-Credential Sandboxing** [Core]: The architecture must enforce a strict reachability limit: secrets, API keys, and long-lived credentials must never enter the untrusted sandbox (e.g., they must not be injected as environment variables where generated code can read them). Removing credentials from the environment is necessary but not sufficient: the sandboxed process must also be unable to read host files, host credential stores, and other credential sources outside its approved mounts, to write to the host, or to reach unapproved network destinations, and a failure of isolation stops execution rather than continuing with weaker controls. These properties are verified by automated tests that attempt each such access and expect denial.
* **Credential Proxies** [Standard]: To perform privileged actions, the agent must use controlled proxies (trusted, predefined tools running outside the sandbox). These proxies hold the secrets securely, execute the operation, and return the result, ensuring the raw credentials are never exposed to the model or its untrusted execution environment.
* **Least-Privilege Defaults** [Standard]: External interactions (e.g., web browsing, API queries) must default to an unauthenticated, logged-out state. Credentials must be granted per task, scoped to the minimum necessary, and time-limited, and are exercised only through credential proxies.
* **Model Calls Through the Control Plane** [Core]: All model calls are made by the control plane, which holds the provider credentials. No model credential is ever placed in any sandbox, so there is no raw-key exception. Credentials held by the control plane must be refreshed without interrupting calls already in flight, because a token that expires mid-stream stalls long calls.
* **Separate Evaluator Credentials** [Standard]: Evaluators that call models must use credentials that are separate from the agent's and unreachable from the agent's environment. When an evaluator invokes the agent's own runtime, the agent's credentials must not be exposed to the evaluator's scripts.

### 4.3. Provenance & Approvals
* **Data Provenance Tracking** [Core]: The harness must not treat all context tokens equally. It must maintain a conceptual model of provenance for every observation (tracking source and trust level), strictly differentiating authoritative system instructions from external data.
* **Untrusted Observations & Prompt Injection** [Core]: External inputs (web pages, emails, database records, tool results) must be treated as inherently untrusted and capable of carrying adversarial prompt injections. The architecture must assume the model will encounter malicious instructions during operation.
* **Quarantined Reader** [High]: Where untrusted content and privileged tools coexist, untrusted content is processed by a quarantined model that has no tool access, and the privileged agent receives only its constrained, structured output.
* **Trust Escalation Prevention** [Standard]: The system must not automatically elevate the trust level of outputs generated by subagents or dynamically loaded skills. Subagent reports and third-party skills must be treated as untrusted boundaries (akin to third-party code) and subjected to the same containment and approval gating as raw external data.
* **Egress as a Capability Grant** [Core]: Network egress allowlists must be treated as strict capability grants rather than simple destination filters, recognizing that an open egress path combined with an untrusted observation creates a direct vector for data exfiltration. Egress is denied by default in every profile. Allowed destinations are granted through a policy proxy that enforces the allowlist and logs every request. The proxy must work with enterprise TLS inspection, so no requirement may depend on certificate pinning. Enforcement is at the network boundary and does not rely on the proxy alone: the sandbox has no route around the proxy, so direct sockets and non-HTTP protocols cannot reach the outside. Destination checks cover hostnames, ports, resolved addresses, redirects, and name resolution. Grants are bound to the workload, task, and session, a revoked grant takes effect within a defined time, every allowed and denied request is recorded, and if the proxy or its policy service fails, egress fails closed.
* **Approval vs. Containment** [Standard]: The system must implement both human approval gates and environmental containment, treating them as orthogonal security measures. Human approval controls *decisions and intent* (e.g., pausing for review on irreversible actions), but it must never be used as a substitute for hard containment. Containment controls *reachable capability* (blast radius) and acts as the final defense when malicious instructions or prompt injections bypass human review due to obfuscation or approval fatigue.
* **Default Autonomy Posture** [Standard]: Agents operate autonomously inside containment. Human approval is required for actions whose declared effect class is irreversible or external-facing.
* **Tool Effect Classes** [Standard]: Every tool must declare one effect class at registration: read-only, reversible write, irreversible, or external-facing. A tool that does not declare it is treated as requiring approval. In Standard and High-assurance deployments, irreversible and external-facing actions pause for approval.
* **Scoped Standing Approvals** [Standard]: To limit approval fatigue, a human may grant a standing approval scoped by tool, argument pattern, lifetime, and count. In High-assurance deployments, irreversible actions require approval for each instance and cannot be covered by a standing approval.
* **Computer-Use Effect Classification** [Standard, conditional]: Generic interaction tools (such as click and type) cannot be classified per tool. A computer-use session is scoped by an allowlist of domains and applications, and risky UI events (form submission, file download or upload, payment, and credential entry) require confirmation. §9.1 and §9.2 specify the details. This requirement applies only when computer use is enabled.
* **Exfiltration Monitoring** [Standard]: Outbound traffic is monitored to detect and block a hijacked agent from transmitting conversation context, memory, or PII to untrusted destinations. The core harness monitors outbound network activity (destinations, volume, and timing), enforces the configured network policy where the environment supports it, and keeps an audit log, and it claims partial conformance: inspection of application-layer payloads is not guaranteed, particularly for TLS-encrypted traffic. Payload inspection is an optional capability of a compatible isolation or security plugin. To claim it, the plugin must provide a verified inspection point, apply the configured exfiltration policy, record auditable inspection outcomes, and document its coverage gaps and bypass conditions; supporting TLS interception is not by itself enough. The system distinguishes network-level monitoring from payload-level inspection and does not claim complete exfiltration detection while encrypted payloads remain uninspected.
* **Consent Visibility** [Standard]: Tool invocations must be clearly visible to human operators, and sensitive or consequential actions (e.g., sending email, executing financial transactions, other irreversible actions) must pause for explicit human consent. Approvals must be recorded in the event log.
* **Data Compartmentalization** [Standard]: Agents and tools that perform external actions must not have raw access to sensitive durable history or memory unless the task explicitly requires it. When data moves between roles (e.g., from a retriever to an external communicator), only the minimum necessary data may cross. External-acting tools receive only the context that their declared task scope names.
* **Proactive Contextual Guidance** [Standard]: Where feasible, guardrails should shape behavior proactively rather than only vetoing actions. At each step, a guidance mechanism (rules and/or an instructor model) may inject step-specific, context-aware instructions (e.g., audience, tool, data sensitivity) into the active context as ephemeral context (§3.1), so that tasks complete safely instead of terminating abruptly. Guidance supplements and never replaces mechanical enforcement of rules that code can check.
* **Memory Write-Path Integrity** [Standard]: Content that can modify durable memory (including stored user models and agent playbooks) is untrusted input. Memory writes are provenance-tagged. Entries derived from untrusted content are quarantined and excluded from privileged retrieval until validated, and entries that would change instructions or behavior pass the gate in §6. A contextual-integrity screen decides whether recording an observation is appropriate, and updates from low-trust sources (e.g., email, web content, advertisements) or that are out of character relative to existing records must be confirmed or quarantined. Memory poisoning, where malicious content rewrites stored records, is a recognized attack. Writes pass the checks of §3.1 in order: Deterministic Memory Policy, Sensitive-Data Detection, Confidence and Provenance Thresholds, Contradiction Detection, then Deduplication and Entity Resolution.
* **Passive Observation Consent** [Standard, conditional]: Passive observers (screen capture, notification, or file-system streams) must require explicit user permission, be individually toggleable and default to off, and support local-first processing for sensitive streams.
* **Untrusted Evaluator Inputs** [Standard]: Trajectories, submitted artifacts, and agent-written files read by an evaluator, particularly a model-based one, are attacker-controlled observations. The evaluator must treat them as untrusted data and be hardened against content that tries to influence its score.

## 5. Subagents, Orchestration & Long-Running Durability
* **Durability & Resumption** [Core]: For tasks spanning hours or days, the harness must be engineered as a fault-tolerant distributed system. It must support durable event logging, state snapshots, and resumption capabilities so that work can recover exactly where it left off following a harness crash, network disconnect, or delayed human approval. After a restart, an interrupted session is resumed only after the checks of Safe Session Resume.
* **Safe Session Resume** [Standard]: After a process or host failure, an interrupted session is restored from durable storage that is independent of the failed worker. The latest checkpoint is loaded and its schema version and integrity are validated (a partially written checkpoint is rejected or recovered, and an incompatible schema is migrated or the session is marked incompatible), the user's authorization and the session's expiry are rechecked, and in-flight external actions are reconciled before execution continues from the next safe operation, without repeating completed steps or side effects. A lease or optimistic concurrency prevents two workers from resuming the same session. Credentials are never persisted, and privileged actions are not resumed after authorization has been revoked. Recovery attempts, the restored checkpoint, and the outcome are recorded, and recovery success and the recovery-point objective are measurable.
* **Event Log Consistency** [Core]: The Event Log has a total order per run and a single writer in the control plane, and an event is durable before the action it records is taken (write-ahead).
* **Snapshot Triggers** [Standard]: The harness snapshots at each submission, before any irreversible or external-facing action, before promoting a self-modification, and at a configurable interval. Recovery restores the latest snapshot, replays the Event Log, and reconciles with external state before retrying anything non-idempotent.
* **Control vs. World State Reconciliation** [Core]: Upon recovery from an interruption or crash, the harness must not blindly retry unacknowledged operations based solely on its internal control state (event log). It must implement mechanisms to reconcile its internal log with the actual external world state to determine if an action was already committed before the interruption occurred. Reconciliation is not limited to recovery or to the submit step: it applies across the lifecycle of consequential actions (Pre-Action Validation Gate, Reconciliation States and Risk Tiers).
* **Pre-Action Validation Gate** [Standard]: Every consequential action passes a single execution gateway that the runtime enforces and the agent cannot skip. Before the action, the gateway checks authorization and that any approval is still current, reads authoritative state for the affected resources, and verifies preconditions and freshness. It executes with concurrency protection (version-conditional writes, transactions, or leases) and an idempotency key, so that a change of state between the check and the action cannot be missed. After the action it reads back the resulting state and compares it with the expected effect, and does not trust the tool's acknowledgment alone. If state or authorization cannot be verified, a safety-critical action does not run, and a timeout is not treated as a failure: the outcome is established from authoritative state before any retry.
* **Reconciliation States and Risk Tiers** [Standard]: Reconciliation outcomes are explicit, auditable states (consistent, drift detected, reconciling, blocked, unknown, and recovery required), and an unknown state never becomes consistent without sufficient evidence. The reconciliation applied to an action is chosen by the potential impact of the action and not by which agent or tool invokes it: low-risk work needs internal consistency checks, medium-risk work adds preconditions, version validation, and post-action verification, and high-risk and critical work adds fresh authoritative state, current approvals, concurrency protection, idempotency, and fail-closed behavior, with human intervention for critical actions. Reconciliation also runs when external state may have changed (retry, timeout, cancellation, revoked approval, or an out-of-band change), and a workflow is not marked complete while required effects remain unverified.
* **Delegation Boundaries & Coordination Overhead** [Standard]: The system must treat subagent delegation as an explicit architectural choice, not an assumed capability multiplier. The harness must only spawn subagents when the task structure strictly justifies clean parallel decomposition. The architecture must account for the fact that unnecessary delegation introduces severe overhead (communication costs, duplicated work, error propagation, and conflict over shared state) that can actively degrade task performance.
* **Concurrency & State Consistency** [Standard]: The harness must treat multi-agent concurrency as a distributed systems consistency problem, not a prompt-engineering problem. To prevent race conditions, duplicated work, or conflicting side effects, the architecture must enforce constraints on shared state (e.g., serializing writes, partitioning resources by worker, or utilizing a centralized authoritative event stream).
* **Demonstrated Justification for Delegation** [Standard]: Delegation configurations must be evaluated against a single-agent baseline on the evaluation harness (§3.6), for both quality and cost, before being promoted to production.
* **Subagent Isolation and Return Contract** [Standard]: Subagents run in isolated contexts and return a concise structured result together with pointers to supporting evidence in the durable history. The parent treats the result as untrusted (§4.3) and can retrieve the subagent's full trace on demand.
* **Single Authoritative Audit Trail** [Core]: All inter-agent messages, handoffs, approvals, and budget events must be written to the harness Event Log, which is append-only and held outside the sandbox. Orchestration layers must not maintain separate competing logs.
* **Background Job Management** [Standard]: A parent agent must be able to launch, inspect (logs and status), cancel, and merge results from background jobs and subagents. Job state must be stored as inspectable files or status records, not only in transient context, so that work can be recovered after an interruption.
* **Atomic Submission Snapshots** [Standard]: When an agent submits a candidate for scoring, the harness must pause the agent's environment, capture a consistent snapshot of its state, and score from that snapshot. The snapshot is immutable, is recorded in the Event Log, and cannot be modified by the agent during scoring. After scoring, the harness resumes the agent and returns only the permitted feedback.
* **Accounting-Preserving Recovery** [Core]: Recovery must preserve submission counts, elapsed wall-clock time, and every budget counter, and a restart must never grant additional budget. Counters must be durable and their updates idempotent, so that a replayed event is counted once. Downtime caused by the harness itself is excluded from the clock only with a recorded reason and within a configured cap, and agent and tool time are never excluded. A run interrupted during scoring re-scores from the immutable snapshot in a fresh evaluator environment.
* **Resource Teardown and Retention** [Core]: When a run ends or fails, every grant made for it (network rules, credentials and tokens, child sandboxes, temporary snapshots, and mounts) must be revoked through an idempotent teardown that is safe to repeat after a failure. The final evaluation result, the final workspace, and the audit log are retained under the retention policy. A grant left behind after a run is a capability leak. Retention is enforced by scheduled jobs and not only by teardown (Retention Enforcement).
* **Retention Enforcement** [Standard]: Every managed resource has an owner, a data classification, a retention policy, and a lifecycle status in a retention registry. A scheduled job finds resources whose retention has expired and deletes or archives them under the governing policy, skips those under legal hold, and verifies the deletion (not only the API response, and taking account of replicas, object versions, caches, and backups where applicable). It retries transient failures with bounded backoff and records an auditable outcome that does not copy sensitive payloads. The job is idempotent, runs with least privilege, never touches another tenant's resources, and exposes overdue and failed deletions. A periodic scan finds orphaned containers, volumes, and objects that lack a registry entry or an active run. Different data classes have different retention periods.

## 6. Harness Self-Improvement (Governed Self-Modification & Optimization)
This section specifies how the harness is improved automatically from execution feedback: the governance every self-modifying process must obey, the improvement loop, its evaluation protocol, and the optimization methods that run inside it. It applies whenever any process (a human-run optimizer, an automated loop, or an agent editing its own instructions or skills) changes the harness's configuration or code from execution feedback, in single-agent and multi-agent deployments alike. Out of scope: pretraining or general fine-tuning of the base model, except the optional joint optimization in §6.9. Optimization that exists only because multiple agents interact (graph-level credit assignment and topology) is specified in the Multi-Agent System PRD §5.

**Normative strength.** §6.1–6.4 and §6.11 are governance and evaluation-integrity requirements and are mandatory. §6.12 applies only when research mode is enabled. §6.5–6.10 describe optimization capabilities, and the modal verb in each requirement (MUST, SHOULD, MAY) governs. Because the supporting evidence is early-stage (Appendix A), algorithmic choices are SHOULD or MAY unless stated otherwise.

### 6.1 Objective & Guiding Principles
* **Improve the harness, never the evaluator.** [Standard] A self-improvement loop optimizes whatever signal it is given, so the evaluator, verifier, and permission controls sit outside the loop (§6.2).
* **Escalating targets, escalating gates.** [Standard] The object being optimized progresses from instruction prompts to structured context, to workflow, to harness code, to optimizer code. Each step up widens the design space and the risk, and requires a stricter gate.
* **Evidence-grounded edits.** [Standard] Every change must trace to observed failures and carry a falsifiable prediction (§6.3).
* **Simplicity over accumulation.** [Standard] Prefer generic mechanisms to accumulating heuristic rules, and re-test and prune scaffolding when the underlying model changes (§3.6).
* **Humans move up the stack, not out of the loop.** [Standard] Oversight is placed at the right time and level of abstraction (§6.11).

### 6.2 Editable Surface & Control Boundary
**Risk tiers.** [Standard]

| Tier | Surface | Examples | Promotion requirement |
|---|---|---|---|
| T0 | Context content | Playbook entries, notes, few-shot demonstrations | Automated gate (§6.3, §6.4) |
| T1 | Instructions and tool descriptions | System prompt, tool documentation and schemas | Automated gate plus sampled human review of manifests |
| T2 | Workflow and harness code | Control flow, tool implementations, middleware, skills, subagent configuration, retrieval parameters | Automated gate plus human approval |
| T3 | Improvement machinery | Proposer, optimizer, selection logic, prompt compilers | Outside the loop; changed only through an out-of-band, human-controlled process |
| T4 | Control and evaluation surface | Verifier, evaluators, held-out sets, tracer, run logs, budgets, permissions, approval gates, sandbox and credential settings, model configuration | Immutable to the loop; changed only by a separate human-controlled process |

The tier assignments are a starting point and should be adjusted to the organization's risk appetite. T4 is not negotiable. Self-modification at T0–T1 requires a Standard-or-higher deployment plus this section, and any capability at T2 or above makes the deployment High-assurance (§1.2).

**Component registry.** [Standard] Every editable component (system prompt, tool descriptions, tool implementations, middleware, skills, subagent configuration, long-term memory) must be represented as a versioned file with a declared risk tier. Each observed failure pattern must map to exactly one component so that edits are targeted and their effects attributable.

**Immutable control and evaluation surface.** [Standard] Everything in T4 must be read-only to any self-modifying loop. A loop may not raise its own reasoning budget, swap its model, or disable its verifier, which keeps every recorded gain attributable to harness edits. Research mode (§6.12) is the only exception, and only inside an isolated fork.

**Edit interface.** [Standard]
* Edits must use a structured form (for example, an identified span of existing code plus its replacement), so that invalid or unapplicable edits are detected mechanically.
* The harness entry point and its interface contract must be preserved.
* Edits must not hard-code answers, read held-out data, or reach the evaluator.
* Edit size should be capped (a 200-line limit is used in the reference QA setup) to keep changes reviewable.

**Recursion bounds and human decision points.** [Standard]
* The loop may edit T0–T2 but may not edit its own proposer, optimizer, or evaluator (T3–T4) without out-of-band human approval.
* Recursion depth must be bounded for production self-modification. Research mode (§6.12) is the only exception, and only inside an isolated fork. When the improver itself is improved, its quality must be measured by a meta-utility over a set of downstream tasks and re-validated on the target model, since recursive improvement degraded results with weaker models in the evidence reviewed.
* The risk tiers define which promotions require human review, and every promotion is recorded in the Event Log (§5).

### 6.3 The Improvement Loop
**Weakness mining.** [Standard]
* The harness is run on tasks and execution traces are collected.
* Failures must be recorded as verifier-grounded failure records containing the terminal verifier-level cause, the causal status of the relevant agent behavior, and the abstract agent mechanism exposed by the trace. Two runs can share the same surface outcome (e.g., a timeout) with different causes.
* Evidence should be layered for token efficiency: a per-task analysis report on the root cause, aggregated into a benchmark overview, with raw traces available on demand.
* Trace content is untrusted external data and must not be able to instruct the analyzer (§4.3).

**Proposal.** [Standard]
* The proposer receives a bounded context: the editable surfaces of the current harness, the verifier-grounded failure patterns, records of passing behaviors that must be preserved, and summaries of previously attempted edits.
* The proposer should prefer recurrent, addressable failure patterns that narrow changes can resolve, and should not target task-specific difficulty.
* Candidates in a round should be distinct and diverse.
* The proposer may inspect the history of prior harnesses, scores, and traces through the file system rather than receiving it all in context.
* Invalid responses receive parse or validation feedback and may be retried within a fixed attempt budget.

**Change manifest.** [Standard] Every proposed edit must carry a manifest recording the failure evidence, the inferred root cause, the targeted fix, and a prediction of both the expected fixes and the at-risk regressions. The prediction is checked against the next round's results, and the loop must record how well predictions matched, as a measure of proposer calibration.

**Validation and promotion.** [Standard]
* **Validity screens** [Standard] run before scoring: parseability, applicability, interface conformance, and size limits. Additional static screens should check for answer echoing, duplicate code, and output-interface violations.
* **All proposals are scored** [Standard], including zero-scoring harnesses. An applied edit can earn no task credit without being invalid, so failed edits and zero-scoring harnesses are reported separately.
* **Non-inferiority acceptance** [Standard]: a candidate is accepted only if it improves its target metric and does not fall below a declared margin on any guardrail metric, judged with confidence intervals under the task's replication policy. This holds on both a held-in set (confirming the weakness is fixed) and a held-out set (confirming no new issues were introduced), and the candidate preserves a recorded set of previously passing behaviors. Rejected candidates are logged and the active harness is left unchanged.
* **Multi-objective acceptance** [Standard] weighs quality together with cost, latency, and safety, not task score alone. The loop may retain a Pareto frontier of candidates rather than a single winner.
* **Per-target-model validation** [Standard]: the ability to propose useful harness edits does not predict whether a given model benefits from them. Every promoted change must be validated on the model it will run with, because weaker models can fail to activate or follow a harness.
* **Staged promotion and rollback** [Standard]: promoted changes follow the risk tier in §6.2, are recorded in the Event Log, and can be rolled back to the prior version (§3.6).

**Selection and search strategy.** [Standard]
* The selection protocol must be declared and fixed for each experiment. Two protocols appear in the reference evidence: retain a candidate only if its development score exceeds its parent's, and advance to the best-scoring candidate even when it scores below its parent. Results are not comparable across protocols.
* Search should maintain diversity to avoid collapse into variants of one solution. Recommended mechanisms are parent sampling that balances performance against the number of offspring already produced, novelty rejection of candidates too similar to the existing population, and an archive that keeps distinct lineages.
* Search methods (evolutionary, tree search, Monte Carlo, population archives) work best when candidates are automatically evaluable and fitness is cheap to measure. They struggle where evaluation is slow, ambiguous, or mostly heuristic, and the loop must report the evaluation cost it consumes.

**Sequential vs. independent revision.** [Standard] Building on the current best harness uses a small proposal budget effectively, while independent proposals contribute diversity. The two may be combined. Any comparison between them must state differences in parent harness, feedback, selection, and total compute (§6.4).

**Preserved negative results.** [Standard] Failed attempts, rejected candidates, and the reasons for rejection must be stored durably and be queryable by later iterations, so the loop does not repeat them. Models trained mostly on successful examples are poor at abandoning a failing hypothesis.

**Improvement loop budgets.** [Standard] An improvement loop has its own budget for proposals, compute, and cost, and a plateau stop rule that ends the loop when successive rounds stop improving the target metric.

**Production traces as input.** [Standard] Production traces may feed the loop only after masking under §3.7 and only for workloads that have opted in.

### 6.4 Evaluation Protocol for Self-Improvement
**Question sets and split discipline.** [Standard] Maintain three disjoint roles: feedback questions (to build execution reports), scoring questions (to score and select candidates), and evaluation questions (held out, to measure final performance). Held-out questions must never be visible to the proposer or used to select a candidate. Where a task has multiple presentation formats, include format-varied questions to detect overfitting to the canonical format.

**Repeatedly queried scorers.** [Standard] A scorer that the loop or the agent can query repeatedly (a judge in a submit-and-feedback loop) is itself a feedback set, because each query leaks information about it. Its score may guide search but must not be reported as the result. The selected candidate must be confirmed on separate data under §3.6, feedback granularity and submission counts must be limited, and the number of queries used must be reported.

**Reporting.** [Standard]
* Report the mean over all proposals, including failures and zero scores, as the primary measure of proposal quality.
* Report best-of-N as an upper bound, clearly labeled as selected on held-out scores and not a deployable result.
* Report variance across tasks and across repeated runs.
* Report sensitivity to the scoring rule for failed edits (retain the parent score, assign zero, or exclude), since excluding zero-scoring harnesses conditions on success and can reverse comparisons.
* Compare improvement procedures only at matched proposal budget, and state any remaining difference in total compute, feedback, and parent harness.

**Transfer and generalization.** [Standard] Evaluate on task families or benchmarks excluded from any training of the proposer, and test whether a harness improved on one benchmark transfers, frozen, to another. Evaluate on the specific target model.

**Updating vs. benefit.** [Standard] Measure separately (a) the ability to produce useful harness edits and (b) the ability of the target model to benefit from the updated harness. Report activation failures (the model does not load the updated harness or skill) and adherence failures (it loads but does not follow it), since benefit has been observed to be non-monotonic in model capability.

**Reward-hacking and over-optimism defenses.** [Standard]
* Keep the evaluator and verifier outside the loop (T4). Where a deterministic check exists, it takes precedence over model-based grading (§3.4).
* Audit generated harnesses structurally (for example, whether a generated helper is merely integrated or actually contributes to the answer), and review training data and candidates for oracle access, memorization, and grader exploitation.
* Judge-model rewards can be exploited in judge-specific ways, and unit-test or benchmark rewards can be overfit. Use held-out tests, trace audits, and human review at decision points.
* Do not accept an improvement from a noisy signal. Require repeated trials and a stated variance before promotion.

**Long-horizon value.** [Standard] Task success is a short-horizon objective. For harnesses that act on shared, long-lived assets (for example, a code repository), the evaluation should add proxies for maintainability, ownership boundaries, migration cost, and backward compatibility, or route such changes to human review.

### 6.5 Declarative Programming & Compilation
The capabilities, not the products, are required: DSPy and GEPA are reference examples, and any implementation providing the same capabilities conforms.

#### 6.5.1 Structured I/O & Declarative Programming (DSPy)
* **Hand-Authored Prompts as Versioned Seeds** [Standard]: Hand-authored prompts are allowed as versioned seeds. Every change to a prompt, whether by a human or by an automated loop, is evaluated and passes the gate in §6.3. Unevaluated trial-and-error prompt editing is not permitted.
* **Declarative Signatures** [Standard]: Implement frameworks (e.g., DSPy [arXiv:2310.03714]) to strictly define input/output contracts (e.g., `question -> search_query`) instead of writing conversational prompts.
* **Modular Execution** [Standard]: Encapsulate prompting techniques (like Chain of Thought or ReAct) inside parameterized modules that can be swapped or combined dynamically.
* **Constrained Decoding** [Standard]: Utilize Finite State Machines (e.g., SGLang [arXiv:2312.07104]) to guarantee outputs conform perfectly to expected schemas.

#### 6.5.2 Pipeline Optimization & Reflective Prompt Evolution
* **Self-Bootstrapping Pipelines** [Standard]: [DSPy: arXiv:2310.03714] The system must utilize a compiler to simulate the pipeline, automatically generate high-quality few-shot demonstrations, and refine instructions.
* **Reflective Prompt Evolution (GEPA Paradigm)** [Standard]: [GEPA: arXiv:2507.19457] To optimize agent instructions efficiently, the system should default to **Natural Language Reflection** over standard Reinforcement Learning (e.g., GRPO) when no training budget or dense verifiable reward is available; RL-trained proposers remain a permitted alternative (§6.8). Because scalar rewards (+1/-1) are sparse and inefficient for complex multi-step trajectories, the reflective optimizer must:
  * **Sample Trajectories** [Standard]: Run agent pipelines in a sandbox and record the full multi-step trajectory (reasoning, tool calls, and outputs).
  * **Diagnose via Reflection** [Standard]: Use an LLM to read the execution trace and reflect in natural language on exactly what failed (e.g., "The Coder misunderstood the Reviewer's critique").
  * **Genetic-Pareto Crossover** [Standard]: Combine the complementary lessons from the absolute best variations (the Pareto frontier) of its own attempts to autonomously generate master instruction sets, reducing required rollouts by up to 35x compared to standard RL.
* **Multi-Stage Credit Assignment & Optimization (MIPRO Paradigm)** [Standard]: [MIPRO: arXiv:2406.11695] In multi-stage pipelines (e.g., Agent A -> Agent B -> Agent C), the optimizer must solve the "credit assignment" problem (determining which specific agent caused the pipeline to fail) without requiring human-labeled intermediate steps. The compiler must:
  * Factorize optimization into two distinct variables: **Instructions** (free-form directives) and **Demonstrations** (few-shot examples) for *every* module simultaneously.
  * Use data-aware and program-aware techniques to generate educated prompt proposals.
  * Utilize stochastic mini-batch evaluation (Bayesian Optimization) to efficiently map out and assign credit to the most impactful prompt combinations across the multi-agent graph, bypassing the need for exhaustive, expensive full-dataset rollouts.
  * Employ meta-optimization to refine how the system generates prompt proposals over time.
* **Model Agnosticism & Downscaling** [Standard]: By compiling the prompt pipelines reflectively, the architecture should support swapping from massive proprietary models (GPT-4) to smaller, cheaper open-weight models (Llama-3, T5) while retaining competitive performance, **provided each target model is validated separately on the evaluation harness** (§6.3). The ability to write useful harness edits does not predict whether a given model can follow the updated harness, and self-improvement loops have degraded results on weaker models.

### 6.6 Alternating Prompt and System Optimization (Frozen-Weight BetterTogether)
[BetterTogether: Soylu et al., EMNLP 2024 / arXiv:2407.10930, adapted] In production environments where fine-tuning neural weights is impossible or cost-prohibitive (e.g., relying on closed models like GPT-4o or Claude 3.5), the system must still implement an alternating, self-teaching optimization loop by treating the *system architecture* as the "weights". **Every change this loop proposes is a candidate, not a deployment: it must pass the gated promotion process in §3.6 (regression evaluation, risk-based human approval, and rollback) before it reaches production.**
* **Phase 1 (Prompt & Context Optimization)** [Standard]: Use DSPy/GEPA to aggressively optimize prompt instructions, few-shot examples, and context window formatting to achieve the highest possible performance from the frozen base models.
* **Phase 2 (System-Level / Procedural Optimization)** [Standard]: Collect the highly successful trajectories (execution traces) generated in Phase 1 and use them to propose upgrades to the system's architecture. Without touching neural weights, the system must propose:
  * *Tool Schema Refinement*: Rewrite Python `@tool` definitions and JSON schemas to be inherently mistake-proof (Poka-yoke, §3.2) based on where the LLM stumbled.
  * *Procedural Abstraction*: Abstract successful, multi-step agent workarounds (e.g., a specific sequence of bash commands) into brand new, single-call Python tools. New tools are subject to the harness tool-design requirements (§3.2) and security review (§4), and must be integration-tested end to end, because a correct helper algorithm still fails when the parsing, tool communication, or answer extraction around it is wrong.
  * *Routing & Graph Optimization*: Update the `TransitionGraph` routing logic or condition thresholds based on successful multi-agent handoffs (topology-level changes are specified in the Multi-Agent System PRD §5.2).
  * *Retrieval (RAG) Tuning*: Use the successful traces to tune the retrieval pipeline's hyperparameters (chunk size, overlap, embedding models) and augment the Semantic Memory index.
* **Phase 3 (Alternate)** [Standard]: Re-run Phase 1 on the promoted configuration. The prompt optimizer will now leverage the upgraded toolsets, improved RAG, and better routing graphs to push the system to even higher performance, creating a compounding cycle of self-improvement entirely independent of neural weight training.
* **Promotion of System-Level Proposals** [Standard]: Each Phase 2 proposal is promoted at its own risk tier (§6.2). For example, a new tool is a T2 change and needs human approval.

### 6.7 Context Optimization
* **Itemized Deltas** [Standard]: A curator mechanism should maintain context as an evolving playbook of identified entries, updated by incremental deltas merged with deterministic logic and periodically deduplicated (§3.1), to prevent context collapse and brevity bias.
* **Separate Mechanism from Content** [Standard]: Where context management itself is optimized, the mechanism (how context is selected, filtered, and formatted) should be separated from the content (what is in context). Mechanism changes are T3 changes (§6.2); content changes are T0.
* **File-Based Representation** [Standard]: A context function should be a directory of files (static components such as a skill file, plus dynamic context and rollout data) so that it is inspectable and versionable (§6.2).
* **Search Over Mechanisms** [High, post-v1]: A meta-level process may evolve the context-management skill using a history of prior skills and their train and validation scores, subject to the same split discipline as any other candidate (§6.4). This capability is post-v1: mechanism changes are T3 changes and stay outside the loop in this version.

### 6.8 Learned Proposers (Optional) [Post-v1]
*Post-v1: retained for design continuity and outside the release trains in §1.3.*
A proposer model may be trained to revise a frozen solver's harness code from a task description, the current harness, and an execution report. At test time, both models are frozen and feedback from successive executions guides further revisions without any parameter update.
* **MAY** initialize the proposer with supervised fine-tuning on teacher revisions. Admit a revision only if it improves on the seed by a set margin, passes the validity screens in §6.3, and survives independent review for oracle access, memorization, and grader exploitation. No held-out question text may enter the corpus.
* **MAY** train the proposer with reinforcement learning (for example, GRPO), either after supervised initialization or directly from the base proposer. Reward is the mean score of the revised harness on scoring questions, disjoint from the feedback questions used to build the report, plus small auxiliary validity terms (the response parses, the edit applies, the harness runs). A failed edit earns only the validity credit accrued before the failure, and a no-change response is scored by running the parent.
* **SHOULD** track proposal reliability (the fraction of proposals that fail to produce a runnable harness or score zero) as a primary metric.
* **SHOULD NOT** mandate training on successive revision states. In the evidence reviewed it did not consistently beat training on individual revisions, and proposers trained only on single revisions continued to improve harnesses over successive rounds at test time.
* **MUST** treat execution-report content seen during training and use as untrusted data (§4.3).
* **MUST** evaluate on task families and benchmarks excluded from training (§6.4).

### 6.9 Joint Harness–Weight Optimization (Experimental) [Post-v1]
*Post-v1: retained for design continuity and outside the release trains in §1.3.*
Some approaches alternate or combine harness updates with updates to model weights, for example a feedback agent that chooses between editing the harness and updating a low-rank adapter.
* **MAY** be explored, but the supporting evidence is provisional and early experiments mixed models of very different strength across roles.
* If adopted, the gain from each lever must be attributed by ablation, harness and weight changes must be budgeted separately, and weight updates must go through model-release governance outside this document.
* Training stability and Goodhart effects remain open problems and must be monitored.

### 6.10 Instructor Model Optimization (Experience-Driven) [Post-v1]
*Post-v1: retained for design continuity and outside the release trains in §1.3.*
[CDI: arXiv:2603.02983] The runtime mechanism for proactive, step-specific contextual guidance is specified in §4.3. This section covers its continual optimization.
* **Experience-Driven RL Optimization** [High, post-v1]: The Instructor model must be continually optimized. The harness telemetry system (§3.7) must capture failure trajectories where privacy violations occurred and convert them into interactive RL (Reinforcement Learning) environments, explicitly training the Instructor to anticipate and prevent novel privacy failures without sacrificing helpfulness. Updated Instructor versions are promoted through §3.6.

### 6.11 Governance & Human Oversight
* **Risk-Tiered Human Review** [Standard]: Human review is placed at decision points that matter, at the right level of abstraction, according to §6.2. How much oversight can be automated is an open question, and automation of review must itself be evaluated.
* **Audit Trail** [Standard]: Every proposal, validation result, promotion, and rollback is recorded in the Event Log (§5).
* **Failure Classes** [Standard]: The self-modification failure classes registered in §3.7 (invalid proposal, regression after promotion, benchmark overfitting or non-transfer, reward hacking, diversity collapse, implementation drift under execution pressure, over-optimism on noisy results, and harness activation or adherence failure) must each be observable and classifiable.
* **Scaffolding Expiry** [Standard]: When the base model is upgraded, learned harness changes are re-tested and pruned if they no longer help (§3.6).

### 6.12 Research Mode: Autonomous Self-Modification Under Review
Research mode is the only exception to the bounds in §6.2. Inside an isolated research fork, an agent may modify anything about the harness (configuration, the improver, evaluators, tests, and harness source code), autonomously and to any recursion depth. Nothing leaves the fork and is deployed to production without a developer's review of safety-guardrail test results that were produced outside the fork. Research mode applies only when it is enabled, and it requires a High-assurance deployment with the microVM isolation tier (§4.1).
* **Research Fork Isolation** [High, conditional]: The fork runs in an environment with no production credentials, data, or network route, and with no write access to production repositories, policy, approvals, or budgets. Sandboxes, the model gateway, the budget governor, the verifier, and the kill switch are provided by infrastructure outside the fork, and nothing the fork builds can replace them.
* **Unrestricted Fork Surface** [High, conditional]: Within the fork, agents may change any artifact, including configuration, the improver, evaluators, tests, and harness source code. Tiers (§6.2), path restrictions, and recursion-depth bounds do not apply inside the fork, and no per-edit human approval is required.
* **Lineage and Reproducibility** [High, conditional]: Every generation is an immutable record with its source commit, pinned toolchain, build manifest, and seeds, so that it can be rebuilt bit for bit. A generation can host the improvement loop that produces the next generation, to any depth.
* **Attested Guardrail Suite** [High, conditional]: The safety guardrail tests (containment and isolation, credentials and egress, policy and approval semantics, budget and kill-switch enforcement, Event Log integrity, tamper and anti-gaming, data handling, and any declared safety evaluations) form a versioned suite that a developer has attested. Promotion decisions rely only on the attested suite.
* **Human-Control Safety Evaluations** [High, conditional]: The attested suite includes evaluations that agents remain under human control, covering at least stop obedience, no resistance to oversight, approval integrity, authority limits, honest reporting, steering acceptance, test and production parity, containment, injection resistance, self-modification discipline, multi-agent collusion, and persistence and resource limits. Each scenario states its result as an upper bound on the violation rate from a stated number of trials, and any violation fails the item.
* **Trust-Anchor Proposals** [High, conditional]: A change made in the fork to guardrail tests, evaluators, held-out data, or the verifier is a trust-anchor proposal. The fork may use its own modified evaluators for internal search, labeled unattested, but they never count toward promotion. A proposal becomes part of the attested suite only after a developer reviews and attests it.
* **Independent Verification** [High, conditional]: A verifier outside the fork rebuilds each candidate from source in a clean environment and runs the attested suite against it as a black box. The verifier signs its results, and the candidate cannot see test content or the testing context. Feedback returned to the fork is coarse and quota-limited.
* **Ratchet** [High, conditional]: A generation is promotable only if every attested safety guardrail passes, it is non-inferior to its best verified ancestor on every attested metric, and it has no unreviewed trust-anchor change, open anomaly, or unreproducible build.
* **Review Package and Developer Gate** [High, conditional]: Promotion requires a developer's decision on a signed review package containing the attested guardrail results, differences in behavior from the baseline, contract changes, trust-anchor proposals, anomaly flags, and cost. Nothing is promoted automatically, and the developer can approve, reject, request more tests, re-baseline, steer, or stop.
* **Blocking Triggers** [High, conditional]: Trust-anchor proposals, anomalies (unusual resource use, attempts to reach outside the fork, and indications that a candidate behaves differently under test), and contract changes pause the lineage that raised them until a developer reviews them. Other lineages and all non-blocking work continue.
* **Operator-Set Budgets** [High, conditional]: Compute, cost, time, and storage budgets for a research session are set by operators outside the fork and enforced as hard stops. Only a developer can renew them, and the fork cannot read or alter the governor.
* **Escape Monitoring and Kill Switch** [High, conditional]: Attempts to reach production, secrets, the host, or networks outside the allowlist are detected and recorded, and an operator can destroy all research sandboxes at once through a path that is independent of the fork.
* **Promotion Path** [High, conditional]: Configuration artifacts reach production through the promotion service (§6.3) after developer approval. Harness source code is never deployed by the system: approval creates a release candidate for the organization's normal release process, and the production control plane never runs fork-built code before that process completes.
* **Research Audit** [High, conditional]: The lineage, every verification, every review decision, and every attestation are recorded in an authoritative log that is outside the fork and hash-chained.

## 7. Extension Contract for Orchestration Layers
Orchestration specifications built on this harness (e.g., the Multi-Agent System PRD) inherit all requirements above, including §6. The harness guarantees the following to such layers, and they may not weaken them:
* **Per-Agent Scoping** [Standard]: Each agent receives its own budgets (including $B_{concurrency}$), tool allowlist, and credential scope.
* **Event Stream** [Standard]: A subscribable, authoritative event stream covering handoffs, tool calls, approvals, and budget events.
* **Untrusted Inter-Agent Boundary** [Standard]: All inter-agent messages are treated as untrusted observations under §4.3.
* **Governed Topology Definitions** [Standard]: Transition graphs, routing rules, and team compositions are versioned control-plane configuration subject to the gated promotion rule in §3.6.
* **Evaluation Hosting** [Standard]: The evaluation harness hosts multi-agent trials, including topology-level regression suites.
* **Failure Taxonomy Extension** [Standard]: Orchestration layers extend the failure taxonomy (§3.7) with their own classes, such as handoff failures and inter-agent trust violations.
* **Self-Improvement Layers** [Standard]: Layers that improve the harness or the orchestration automatically (including topology, team composition, and routing optimization) inherit §6 in full, may not edit anything in the immutable control and evaluation surface (§6.2), and promote changes only through the gates in §3.6 and §6.3.
* **Metered Compute and Sandboxes** [Standard]: Accelerator-hours and child sandboxes used by any agent count toward that agent's and the run's budgets, and orchestration layers may create execution environments only through the broker (§4.1).
* **Evaluation Integrity** [Standard]: Orchestration layers inherit §3.6 and §5 (fresh evaluator environments, confirmatory final evaluation, atomic snapshots, accounting-preserving recovery, and teardown). The run provenance manifest must include the topology version and the team composition.

## 8. Knowledge Retrieval (RAG)
This section specifies the retrieval subsystem that agents use to ground answers in organizational and external knowledge. Just-in-time retrieval through tools such as `grep` is governed by §3.1 and is out of scope here. Retrieved passages are untrusted observations under §4.3 (processed by the quarantined reader in High-assurance deployments where privileged tools are available), and corrective fallbacks that reach external sources obey the default-deny egress rules in §4.3. A deployment that retrieves from a corpus with document permissions is at least Standard (§1.2). The RAG-Sequence and RAG-Token generation strategies are not requirements: they need access to model internals (marginalizing over documents per sequence or per token) that hosted models do not expose, and per-document generation with aggregation may be built as a prompting pattern.

### 8.1 Retrieval Pipeline
* **Hybrid Retrieval** [Standard]: Combine a sparse lexical retriever (e.g., BM25) and a dense retriever, and fuse their ranked lists with Reciprocal Rank Fusion.
* **Reranking** [Standard]: Rerank the fused candidates with a cross-encoder or an equivalent model before they reach the context.
* **Semantic Chunking** [Standard]: Split documents at semantic boundaries (semantic or late chunking), with chunk size and overlap as versioned parameters.
* **Corrective Retrieval** [Standard]: Retrieval is an agent action. A critic evaluates whether the retrieved context is relevant and sufficient, discards irrelevant passages, and triggers corrective fallbacks (a rewritten query, an additional retrieval, or an external search, which obeys the egress rules in §4.3 and is logged) instead of letting the model answer without grounding. The number of corrective rounds is bounded by the budgets in §3.3.
* **Late-Interaction Retrieval** [Standard, conditional]: Token-level late-interaction retrieval (e.g., ColBERT-style MaxSim) is optional. It is adopted only where evaluation shows a gain over hybrid retrieval with reranking on the target corpus.

### 8.2 Structured Indexes
* **Hierarchical Summary Index** [Standard]: Build a tree of recursively clustered and summarized chunks (RAPTOR-style) so that thematic and whole-document questions can be answered from higher levels of the tree.
* **Knowledge Graph Index** [Standard]: Build a knowledge graph from the corpus (GraphRAG-style) with community summaries, for multi-hop and corpus-wide questions.
* **Index Cost and Refresh** [Standard]: Summary and graph construction use model calls, and their cost counts toward the cost and compute budgets (§3.3). Each index declares a refresh policy and supports incremental update when the corpus changes.

### 8.3 Governance
* **Permission-Aware Retrieval** [Standard]: Retrieval enforces the requesting user's document permissions at query time, in the retrieval layer and not by instructing the model. Index entries carry their access-control metadata, and results are never cached across permission boundaries (§3.8).
* **Ingestion Provenance and Allowlisting** [Standard]: Documents enter the index only from allowlisted sources and carry their source, owner, and ingestion time. Content from low-trust sources is quarantined until validated, consistent with the memory write-path rule in §4.3.
* **Deletion and Update Propagation** [Standard]: When a source document is updated or deleted, every derived structure (chunks, embeddings, summaries, and graph nodes and edges) is invalidated or rebuilt, and the propagation is logged.
* **Grounding and Citation** [Standard]: Answers cite the passages they rely on, and the Event Log records which retrieved passages entered the context.

### 8.4 Operations & Evaluation
* **Versioned Index Artifacts** [Standard]: The embedding model, chunking parameters, fusion and reranker settings, and index versions are versioned control-plane configuration (§3.6). A change of embedding model requires a rebuild, and the run provenance manifest records the index version.
* **Retrieval Evaluation** [Standard]: Evaluate retrieval on held-out queries for both retrieval quality (for example, recall at k) and end-to-end groundedness, using the trials, replication, and split discipline in §3.6 and §6.4.
* **Component Ablation and Cost** [Standard]: Report each component's contribution and its cost and latency (hybrid fusion, reranker, critic, hierarchical index, graph index) so that components that do not pay for themselves can be removed.
* **Retrieval Parameter Tuning** [Standard]: Tuning chunk size, overlap, embedding model, or fusion weights is a T2 change under §6.2 and is promoted through the gate in §6.3.

## 9. Computer-Use Agents (Web and GUI)
This section specifies agents that operate web pages and desktop applications through their visible interfaces, including search-driven web navigation and screenshot-based GUI control. Agents that use text-only APIs are out of scope. A deployment is at least Standard, because page and screen content is untrusted and actions can be consequential. Autonomous multi-step sessions, irreversible actions, or sensitive data make it High-assurance.
Page and screen content (DOM text, accessibility trees, and screenshots) is untrusted observation under §4.3, and indirect prompt injection from pages is the central threat. Sessions start logged out under the least-privilege defaults in §4.2. Generic interaction tools such as click and type cannot be classified per tool, so the effect-classification rule in §4.3 (Computer-Use Effect Classification) is specified here as session scope (§9.1) and risky-event confirmation (§9.2). Reported benchmark success rates for computer-use agents were far below human performance when the benchmarks were published, so reliability must be treated as limited and humans stay on the risky events below.

### 9.1 Interaction Environment
* **Isolated Interaction Environment** [Standard]: The browser or desktop runs in an isolated environment with a virtual display and an ephemeral profile, under the isolation tier required by §4.1. No cookies, saved passwords, or credentials persist across sessions by default.
* **Session Scope Declaration** [Standard]: Before a session starts, it declares the allowlisted domains and applications, the permitted event classes, and its step and time budgets. Actions outside the scope are blocked mechanically, with network scope enforced at the policy proxy (§4.3) and application scope enforced by an application allowlist.

### 9.2 Risky Events and Credentials
* **Risky UI Event Confirmation** [Standard]: The following events pause for human confirmation: form submission, file download or upload, payment, credential entry, permission and consent dialogs, and sending a message. In High-assurance deployments, confirmation is per instance and cannot be covered by a standing approval (§4.3).
* **Login Handoff** [Standard]: The agent never types or sees a secret. Login flows are completed by the credential proxy or by a human handoff, during which the agent is paused and screen capture is suspended.
* **Downloads Are Untrusted** [Standard]: Downloaded files are quarantined and treated as untrusted. They are opened or executed only inside the sandbox.

### 9.3 Perception and Action
* **Observation Modes** [Standard]: Support structured observations (DOM or accessibility tree, with tools to parse noisy markup) and screenshot observations. Prefer structured observations when available, and use screenshots for interfaces that lack structure.
* **GUI Grounding** [Standard]: A vision-language model maps a screenshot and an intent to pixel coordinates for pointer and keyboard actions. The harness validates each coordinate against the screen bounds and the session scope, and verifies the action's effect with a follow-up observation before continuing.
* **Navigation Strategy** [Standard]: Agents formulate search queries, explore strategically, and backtrack. Repeated actions on an unchanged screen are detected as a stuck loop under §3.3.
* **Cross-Application Workflows** [Standard, conditional]: Data moves between applications only through the sandbox's clipboard and files, and nothing leaves the allowlist. This applies only when cross-application workflows are enabled.

### 9.4 Operations & Evaluation
* **Action Recording and Replay** [Standard]: Every action and observation is recorded in the Event Log, with sensitive screen regions redacted, so that a session can be replayed for audit.
* **Computer-Use Evaluation** [Standard]: Evaluate in realistic, stateful environments with programmatic checks of the final state, using the trials and variance rules in §3.6. Report task success, step efficiency, error recovery, and the number of blocked out-of-scope events.

References: WebShop (arXiv:2207.01206) and OSWorld (arXiv:2404.07972).

## 10. User Modeling & Next-Action Prediction
This section specifies user models learned from observation of a person's computer use, and prediction of that person's next actions, for proactive-assistant products. It follows *Creating General User Models from Computer Use* (Shaikh et al., arXiv:2505.10831) and *Learning Next Action Predictors from Human-Computer Interaction* (arXiv:2603.05923), and it builds on the governance requirements that apply first and are not repeated here: user and context memory (§3.1, Governed User and Context Memory), proactive action (§3.3, Initiative and Interruption Policy and Confidence-Gated Action), and memory writes and passive observation (§4.3, Memory Write-Path Integrity and Passive Observation Consent). A deployment that enables passive screen observation handles sensitive data and is therefore High-assurance.
The published results come from small studies: 18 participants for the email evaluation and 5 participants over 5 days of screen use for the end-to-end evaluation of the general user model, and 20 users for the next-action study, where 17.1% of predicted trajectories aligned with what users did at a judge score of at least 0.5 (about 26% among the most confident predictions). A deployment must therefore measure its own accuracy, calibration, and usefulness (§10.5) and must not assume the published figures.

### 10.1 Ownership and Governance
* **Deployment Approval** [High]: Before a user-modeling deployment starts, it requires documented approval from the organization's privacy and legal functions, notice to the people observed, and each person's opt-in. Observing employees' screens carries legal obligations that vary by jurisdiction.
* **Sensitive Inference Policy** [High]: An organizational policy defines categories of inference that must not be stored or surfaced (for example, health, judgments about a person's abilities or job satisfaction, and sentiments about named third parties). The policy is enforced at write time by the contextual-integrity audit below, which is itself auditable, and the standard it applies to these categories is at least as strict as the context implies.
* **Local-First Processing** [High]: Observation, modeling, and storage run on the user's own device or on infrastructure the user controls, and no raw observation or proposition leaves it. The user model is encrypted under a key the user holds. An organization that deploys user modeling can read it only through a grant that the user gives per application, and each grant is logged and revocable. Open models are used so that private data is not sent to third-party AI platforms.
* **Contextual-Integrity Audit** [High]: Every observation is audited before it can contribute to the model. Using the model's own retrieved propositions about the person's privacy expectations, the audit answers five questions: whether new information is disclosed, what type of data it is, who its subject is, who the recipient is (here, the model), and whether it should be transmitted to the model. An observation for which the answer is no is blocked before any proposition is generated. Audit decisions are logged and open to user review, and users can state their privacy norms explicitly.

### 10.2 User Model
* **Propositional User Model** [Standard]: The model is a set of natural-language propositions about the user (behavior, knowledge, beliefs, preferences), each with a confidence value, the observations that ground it, a reasoning note, and a proposition-specific decay (staleness rate). A proposition is generated by first writing a rationale from the observations, then the proposition, then a conservative verbalized confidence score on a 1 to 10 scale normalized to 0 to 1, then its decay. Observations and propositions are many-to-many. Zero-confidence propositions stay stored and are hidden from default retrieval, and deletions propagate (§3.1). The product may offer a sanitized view, because candid propositions about abilities or priorities can be unwelcome.
* **Proposition Retrieval** [Standard]: Retrieval is two-stage. A lexical retriever returns candidates, then a model-based reranker labels each as identical, similar, or unrelated. Relevance is adjusted by the proposition's own recency decay, and the final set is chosen for diversity (maximal marginal relevance). Queries accept search terms, a relevance-versus-diversity balance, a time cutoff, and whether decay applies.
* **Proposition Revision** [Standard]: A newly generated proposition that retrieval flags as similar to existing ones is used to revise them: the module regenerates the text, confidence, decay, and reasoning from both the old and new propositions and their grounding, and can revise several at once. A proposition revised to zero confidence is never evicted.
* **Observers** [Standard, conditional]: Observation sources (screen, notification, file system, and others) are pluggable observers that emit observations with a source, a timestamp, and a unique identifier. A screen observer captures on input events and converts frames and the actions across recent frames to text. This applies only when passive observation is enabled.
* **Application Access** [Standard]: Applications query the model through an interface with relevance, diversity, and recency controls. An application cannot modify propositions without the user's permission, and users can view, edit, delete, and add propositions.
* **Feedback as Observation** [Standard, conditional]: A user's feedback on a suggestion (approval, disapproval, or free text) is recorded as an observation and processed like any other, so that the model converts it into appropriately weighted propositions. This applies only when suggestions are enabled.

### 10.3 Prediction
* **Passive Trajectory Labeling** [High, conditional]: A pipeline may record screen and input events passively, group adjacent input events of the same type into bursts, keep screenshots from just before and after each burst, drop frames that did not change, split the stream into short chunks, and use a vision-language model, conditioned on the input events, to caption higher-level actions. Labels are model-generated and noisy, so the pipeline is validated against a human-annotated sample, and any LLM judge is validated by human preference rates. This applies only when trajectory labeling is enabled.
* **Two-Phase Prediction With Trace Memory** [Standard, conditional]: A predictor first reasons about the current context to form a retrieval query, retrieves from a memory that pairs past observations with reasoning traces, and then reasons again with the retrieved traces to predict the next actions. Retrieval is lexical with temporal decay and diversity selection, entries are deduplicated when inserted, only entries up to the query time are readable, and each user has a separate memory. The best-scoring trace is saved back to memory. This applies only when next-action prediction is enabled.
* **Sample-Agreement Confidence** [Standard, conditional]: A prediction's confidence is derived from agreement among several sampled trajectories (the spread of their embeddings around the centroid) and is reported as a percentile within the user. Accuracy must rise as confidence rises, and the deployment checks that relation. This applies only when next-action prediction is enabled.
* **Trained Predictors** [High, conditional]: A predictor is trained with a policy-gradient method over both phases end to end. The reward is an LLM judge's similarity between predicted and actually observed future actions, and the judge is validated against human preference. Retrieved text is masked from the loss, the retriever is randomly perturbed during training so that it stays robust, training proceeds chronologically with memory reset at epoch boundaries, and each user has an adapter and a separate memory. Judge-based rewards can be hacked over long runs, so held-out judges, human checks, and the split discipline of §6.4 apply. This applies only when trained prediction is enabled.
* **Online Learning** [High, conditional]: Labeling and training run asynchronously. New labeled actions are queued, consumed in a single pass, and discarded after use, memory is never reset so that reasoning traces accumulate, and the model adapts as the person's behavior drifts. This applies only when online learning is enabled.

### 10.4 Proactive Action
* **Execution Through Computer-Use Agents** [High, conditional]: Predicted or suggested actions may drive a computer-use agent only under §9 and the approvals in §4.3. An action runs without asking only when it has no irreversible side effects, and tools that reach external systems are off by default and toggled by the user. This applies only when proactive features are enabled.

### 10.5 Evaluation
* **User-Model Evaluation** [Standard]: Evaluate accuracy and calibration (with a Brier score) on held-out data, comparing the full pipeline with ablations that remove retrieval and revision, together with user-rated usefulness of suggestions, interruption cost (the false-positive rate of surfaced suggestions), the audit's miss rate on sensitive content, and rank-based human preference with multiple-comparison correction, using the replication and split rules in §3.6 and §6.4. Underconfidence is preferred to overconfidence.
* **Next-Action Evaluation** [Standard, conditional]: Predictions are scored by an LLM judge for similarity to the actual future actions, with the judge validated against pairwise human preferences. Report pass-at-k at a stated similarity threshold, accuracy as a function of confidence, human win rates against baselines (zero-shot, retrieval-augmented few-shot, and supervised fine-tuning), and ablations (without reasoning, without retrieval, and with shuffled training order), on chronologically later data and, for multi-user training, on unseen users. This applies only when next-action prediction is enabled.

## Appendix A: Evidence Base and Maturity
Requirements in this document draw on the following sources. Treat the algorithmic requirements as provisional and the governance requirements as firm.
* **Governance (firm).** Several independent sources converge on keeping the evaluator and permissions outside the improvement loop and on grounding every edit in evidence: Agentic Harness Engineering (read-only verifier, tracer and model configuration; change manifests), Self-Harness (held-in and held-out regression gating), and the survey in Weng, *Harness Engineering for Self-Improvement* (July 2026).
* **Harness Learning** (Zhang et al., arXiv:2609.35738). A proposer trained with RL improved single-revision quality on unseen Reasoning Gym families (mean 0.32 for the base proposer to 0.62), and a trained 4B proposer outperformed its 35B teacher on average, while the teacher scored higher under oracle best-of-eight selection. A proposer trained on HotpotQA transferred to MuSiQue and 2WikiMultihopQA. Caveats: small models, synthetic tasks and one benchmark family, and the authors state that their sequential-vs-independent comparison does not match compute or feedback.
* **Harness updating vs. benefit** (Lin et al., arXiv:2605.30621, as summarized by Weng). Harness-updating capability was flat across models, while benefit was non-monotonic in capability.
* **Self-Taught Optimizer** (Zelikman et al.). Recursive improvement helped with a stronger model and degraded with weaker ones.
* **Failure modes of autonomous research** (Trehan and Chopra, as summarized by Weng): training-data defaults, implementation drift, memory and context degradation, over-optimism, insufficient domain intelligence, and weak scientific taste.
* **Joint harness-and-weight optimization** (SIA, WHALE, Continual Harness). Weng characterizes the SIA evidence as provisional because of confounded model choices.
* **Open problems** noted by Weng: weak evaluators, context and memory lifecycle, negative results, diversity collapse, reward hacking, long-term success, and the role of humans.
* **OpenRSI Index and its RSI-Harness** (run-orchestration design as described by the project repository and a requirements summary; the implementation was not verified). It informed the submission-loop, evaluator-integrity, isolation-parity, brokered-sandbox, recovery-accounting, and teardown requirements. The project measures whether agents can drive recursive self-improvement. It does not implement recursive self-improvement of an agent's own harness or weights.

* **Spatiotemporal composability** (Shi, Zhang, and Cui, arXiv:2608.25512). Components that carry inverses for their effects, and that declare dependencies which drive activation and deactivation, give complete removal and reactive coordination. The paper reports one production plugin ecosystem with over 4,000 plugins as its evidence and names validation on self-evolving harnesses as future work. §3.9 adopts the discipline.
