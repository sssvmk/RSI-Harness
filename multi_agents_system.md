# Product Requirements Document (PRD): Multi-Agent System

## 0. Scope & Relationship to the Harness PRD
This document specifies what is **unique to multi-agent systems**: orchestration topology, inter-agent security, graph-level credit assignment, and multi-agent evaluation, plus the data annotation and synthesis pipelines that are built on multi-agent orchestration (§7). It is a companion to, and depends on, the *AI Agent Harness PRD* (`harness_intent.md`), which owns every requirement that must hold even for a single agent, including how prompts, tools, and systems are improved automatically and under what governance (Harness §6). Requirements here carry the same profile tags as the Harness PRD (Harness §1.2).

### 0.2 Binding Rules for This Document
1. **Compaction never deletes raw history.** [Core] Any memory or compaction behavior in an orchestrated system must keep the raw durable history intact (Harness §3.1).
2. **Optimizer-proposed changes are gated.** [Standard] Every change generated by any optimization loop (instructions, demonstrations, tool schemas, new tools, transition graphs, team compositions, retrieval parameters; see Harness §6 and §5 of this document) is control-plane configuration and must pass the gated promotion process in Harness §3.6 and §6 before reaching production.
3. **Sub-agent output is untrusted.** [Standard] Sub-agent reports, summaries, and handoff payloads are untrusted observations under Harness §4.3. Orchestration must never auto-elevate their trust.
4. **No agent grades its own run.** [Standard] The final evaluator of a multi-agent run must be independent of every participating agent in model, context, and credential, or be labeled low-independence and backed by a deterministic or independent check (Harness §3.4). Final results are confirmed under Harness §3.6 before they are reported.

### 0.3 Profile Overlay and Delivery
* **Overlay.** A multi-agent deployment's conformance profile is set by its own risk factors (Harness §1.2). The requirements in this document apply on top of that profile. A workload that uses autonomous open-ended agents is High-assurance by its risk factors.
* **Delivery.** The requirements in this document are delivered in Train 3 (Harness §1.3), after the platform and evaluation train, except §7, which is delivered in Train 4.
* **Post-v1.** Dynamic topology (§2.3) and dynamic compute allocation (§3.1) are post-v1.

## 1. Objective & Guiding Principles
To design and implement a robust, autonomous multi-agent orchestration layer, on top of the Agent Harness, that solves complex, long-horizon tasks reliably and safely using a compound AI approach: a core LLM combined with external tools, structured memory, and advanced reasoning frameworks.

### 1.1 Guiding Principle: Simplicity First & Anti-Brittleness
* **Simplicity & The Single-Agent Baseline** [Standard]: Prioritize simplicity and composability over complex frameworks. Start with direct API calls. If autonomy is needed, strictly prefer a **highly-capable single-agent system** over a multi-agent system [Graham Neubig, OpenHands Blog]. Multi-agent orchestration should only be introduced when task isolation is strictly required, as it inherently introduces rigid structural boundaries, communication overhead, and severe information loss between agent handoffs.
* **Anti-Brittleness (Versioned, Evaluated Prompts)** [Standard]: LLM calls are abstracted as declarative text transformation graphs, so that compilers can automatically optimize instructions and demonstrations. Hand-authored prompts are allowed as versioned seeds, and every change to a prompt, whether by a human or an automated loop, is evaluated and passes the gate in Harness §3.6 and §6.3. Unevaluated trial-and-error prompt editing is not permitted. Compilation and optimization are specified in Harness §6.5.

### 1.2 Admission Criteria for a Multi-Agent Topology
A multi-agent topology is admitted to production only when all of the following hold:
* **Structural Justification** [Standard]: The topology declares one justification type. A *parallelism* topology has a clean parallel decomposition. An *isolation* topology separates context, privilege, or evaluation roles in a way that a single agent cannot.
* **Measured Benefit** [Standard]: The test depends on the declared type. A parallelism topology must beat the single-agent baseline on quality or latency at a matched total budget (tokens, accelerator-hours, wall-clock). An isolation topology must be non-inferior to the baseline on quality within a declared cost uplift and must demonstrate the isolation benefit it claims. Both are confirmed on data not used to select or tune the topology (Harness §3.6).
* **Defined Failure Handling** [Standard]: Handoff failures, coordination conflicts, and budget exhaustion are covered by registered failure classes (Harness §3.7).

## 2. Multi-Agent Orchestration Architecture

### 2.1 Hub-and-Spoke Network & Typed Channels
The system must support specific, composable execution patterns, moving away from monolithic or rigid "GroupChat" classes to a robust, event-driven network architecture (following the AutoGen paradigm [arXiv:2308.08155]).
* **Hub-and-Spoke Network** [Standard]: Orchestration must be handled by a central Hub that owns the agent registry and the topology (transition graph) state. Agents are isolated and communicate exclusively over the Hub. The Hub persists all events through the harness Event Log (Harness §5) and must not maintain a separate write-ahead log or audit trail. All inter-agent traffic passes through the Hub, with no peer-to-peer messaging, so that policy and audit apply to every message.
* **Typed Communication Channels** [Standard]:
  * **Workflow Channels** [Standard]: Deterministic, strict-turn-taking channels governed by a JSON-serializable **Transition Graph** (state machine).
  * **Conversation Channels** [Standard]: Free-form, two-party sessions (e.g., for Evaluator-Optimizer critique loops) where either side can speak dynamically. Each conversation channel must declare a maximum number of rounds and a stop criterion, and completion is verified by an evaluator, never by the generator's claim.

### 2.2 Tool-Driven Handoffs & Execution Modes
* **Tool-Driven Handoffs (Hierarchical Orchestration)** [Standard]: For Triage or Orchestrator-Worker patterns, handoffs between agents must be triggered explicitly via tool calls (e.g., Triage calls `escalate_to_security()`), which emit handoff events evaluated by the Transition Graph. Every handoff is an explicit event validated against the transition graph, and classifier-based routers emit handoff events like any other agent.
* **Execution Modes** [Standard]:
  * **Prompt Chaining** [Standard]: Sequential, pipelined workflow channels.
  * **Routing / Triage** [Standard]: Classification-based delegation via custom routing logic or tool-based handoffs.
  * **Parallelization** [Standard]: Asynchronous, concurrent execution (Sectioning) and multi-attempt aggregation (Voting).
  * **Evaluator-Optimizer** [Standard]: Iterative critique loops between a Generator and a Reviewer over a Conversation Channel.
  * **Autonomous Agents** [High]: Open-ended planning and environmental feedback loops for highly complex tasks. A workload using this mode is High-assurance by its risk factors (Harness §1.2), and every budget dimension applies.
* **Autonomous-Run Oversight** [High]: Autonomous runs publish non-blocking checkpoint summaries visible to operators, and operators have a kill switch that terminates the run. These supplement, and never replace, hard budgets and approvals.

### 2.3 Dynamic Agent Network Topology [Post-v1]
*Post-v1: dynamic capabilities are outside the release trains in Harness §1.3.*
* **Static Teams in v1** [Standard]: Team composition and routing are static configuration. Changes go through the human-approved configuration path (Harness §6.2, tier T2).
[arXiv:2310.02170] To avoid the inefficiency of rigid, hardcoded communication structures, the system must support dynamic, inference-time network topology.
* **Team Optimization** [High, post-v1]: Before executing complex tasks, the Orchestrator must support a "preliminary trial" phase to evaluate a pool of candidate agents.
* **Unsupervised Pruning** [High, post-v1]: Agents must be ranked using an unsupervised metric (e.g., Agent Importance Score based on contribution). Irrelevant or poor-performing agents must be dynamically pruned from the active team to reduce context bloat and token costs.
* **Fluid Routing** [High, post-v1]: Communication between the optimized team must be routed dynamically based on query relevance rather than strict, predefined sequential graphs.
* **Auditability** [High, post-v1]: Team selection, pruning decisions, and routing choices must be recorded in the Event Log with their scores, so that they can be replayed and evaluated.

### 2.4 Sub-Agent Isolation & Handoff Integrity
* **Context Isolation** [Standard]: Heavy exploration is delegated to sub-agents that return only concise summaries to the orchestrator, per the harness return contract (Harness §5).
* **Handoff Payloads** [Standard]: To limit information loss across handoffs (§1.1), a handoff must carry a structured result plus pointers to supporting evidence in durable history, not prose alone. The receiving agent can retrieve the evidence on demand.
* **Untrusted by Default** [Standard]: The Hub must treat every handoff payload as an untrusted observation (§0.2, rule 3) and must not let it carry instructions that expand the receiving agent's tools, credentials, or budgets.
* **Per-Agent Credentials and Sandboxes** [Standard]: Each agent has its own execution environment created through the harness broker (Harness §4.1) and its own metered model-call identity in the control plane, with spend and rate caps. No agent holds a model credential (Harness §4.2). Agents share no ambient credentials or filesystem, and shared state is exchanged only through the Hub or partitioned, inspectable files.

### 2.5 Topology-Level Concurrency
* **Channel Semantics** [Standard]: The Hub must define handoff ordering, per-channel turn-taking, and write partitioning so that parallel agents cannot produce conflicting side effects, within the consistency constraints of Harness §5.
* **Voting and Sectioning** [Standard]: Parallel branches must be isolated in context and shared state until their results are aggregated by the Hub.
* **Recovery Without Double Execution** [Standard]: Hub state (the agent registry, the current position in the transition graph, and pending handoffs) must be recoverable from the Event Log. Replaying a handoff event after recovery must not repeat its side effects, and recovery must preserve every agent's and the run's budget counters (Harness §5).
* **Per-Agent Teardown** [Standard]: When a run ends or fails, the Hub must trigger teardown of every agent's grants, tokens, and sandboxes, including those of agents pruned earlier in the run (Harness §5).

### 2.6 Agent and Handoff Failure Handling
* **Failure Escalation Path** [Standard]: When an agent or handoff fails, the Hub applies a bounded number of retries, then switches to a declared fallback (which may be the single-agent baseline), then escalates to a human. Retries respect the idempotency and effect-class rules in Harness §3.2 and §4.3. Every step is recorded with its failure class (Harness §3.7).

## 3. Model Routing & Reasoning

### 3.1 LLM Core & Compute Routing
* **Instruction Tuning** [Standard]: The LLM core must be tuned for API/tool calling.
* **Cost, Model, and Test-Time Compute Routing** [Standard]: [FrugalGPT: arXiv:2305.05176] Implement an AI Gateway through the harness middleware hooks (Harness §3.8). In v1, routing is static: versioned rules by role and task class, with spend counted against the harness cost budget. Dynamic difficulty estimation and allocation of inference-time compute (Compute-Optimal Test-Time Scaling [arXiv:2408.03314], where a smaller model generates many reasoning paths and self-corrects) is post-v1.

### 3.2 Planning & Reasoning Engine
* **ReAct Implementation (Thought-Action-Observation)** [Standard]: [arXiv:2210.03629] Implement a continuous, interleaved reasoning and acting loop. The agent must generate a "Thought" to induce plans, track progress, and handle exceptions, followed by an "Action" to interface with external tools. The environment must return an "Observation" before the next cycle. This synergy grounds the LLM in external facts (preventing pure Chain-of-Thought hallucinations) and ensures human-interpretable execution trajectories. ReAct-style reasoning is the baseline pattern.
* **Self-Consistency & Reflexion** [Standard]: Generate multiple reasoning paths and maintain self-reflection loops for course correction. These are optional per task and subject to the harness budgets.

## 4. Inter-Agent Security & Safety
Generic safety and security requirements (injection defense, containment, credentials, exfiltration, approvals, privacy compartmentalization) are specified in Harness §4. This section covers only the risks that arise between agents.

### 4.1 Role Integrity & Anti-Sycophancy
* **Multi-Agent Collusion Prevention** [Standard]: Enforce strict role separation and role constraints (preventing *Disobey Role Specification* failures) via the orchestration Hub. Roles are enforced by the Hub through per-role tool and credential scoping.
* **Anti-Sycophancy & Echo Chambers** [Standard]: Design evaluation loops that penalize sycophantic behavior (where a Reviewer agent blindly agrees with a flawed Coder agent). Reviewer independence is labeled (Harness §3.4), and the Hub monitors reviewer agreement rate and alerts on sustained agreement.

### 4.2 Holistic Intent Monitoring (Preventing Sub-Task Bypasses)
* **Graph-Level Intent Monitoring** [Standard]: Standard safety filters on individual agents are easily bypassed by malicious actors who break a harmful task (e.g., deanonymization) into several benign sub-tasks distributed across multiple agents. The central Orchestrator (Hub) must implement graph-level monitoring, analyzing the synthesized state of the entire multi-agent trajectory to detect emergent malicious intent that individual node-level filters miss. The monitor is rule-based or classifier-based over the aggregated trajectory. In Standard deployments it logs and alerts. In High-assurance deployments it can block.

### 4.3 Agent-to-Agent Adversarial Immunity
[arXiv:2508.10880] As agents interact with external systems, they are vulnerable to malicious agents utilizing dynamic social engineering (e.g., impersonation, consent forgery). Simple rule-based constraints (e.g., "do not share data") are insufficient.
* **Identity-Verification State Machines** [High]: Agents handling sensitive data must implement robust, explicit state machines that demand secondary authentication or cryptographic verification before releasing data to external actors or unverified sub-agents. Internal agents receive identities issued by the control plane for each run.
* **External Agents** [Standard]: Agents outside the platform are never Hub members. They are untrusted external services reached through a gateway, and their outputs are untrusted observations (Harness §4.3).
* **Adversarial Simulation Loops** [High]: The optimization pipeline (GEPA, per Harness §6.5) must be utilized not just for task success, but for **Evolutionary Red-Teaming**. The system must automatically pit Attacker agents against Defender agents in simulated sandboxes, using LLM-as-an-Optimizer to iteratively evolve and harden the Defender's prompt instructions against sophisticated, multi-turn conversational attacks. Hardened instructions are promoted only through the gate in Harness §3.6.

## 5. Multi-Agent Optimization (Delta)
The machinery for optimizing prompts, context, tools, and system behavior (declarative compilation, GEPA, MIPRO, BetterTogether, learned proposers) is specified in Harness §6.5–6.10 and applies to single- and multi-agent systems alike. This section covers only what arises from having multiple agents.

### 5.1 Graph-Level Credit Assignment
* **Failure Attribution** [Standard]: In a multi-stage agent graph (e.g., Agent A -> Agent B -> Agent C), the optimizer must determine which agent or handoff caused a failure without human-labeled intermediate steps. The node-specific probes in §6.4 supply the attribution signal.
* **Joint Optimization** [Standard]: Instructions and demonstrations must be optimized for every agent's modules together, using evaluation on mini-batches of the whole graph rather than exhaustive full-dataset rollouts.
* **Full-Graph Regression** [Standard]: An improvement to one agent can degrade another. Every candidate must therefore be evaluated against the full-graph regression suite, not only the changed node.

### 5.2 Topology as an Optimization Target
* **Topology Changes Are Gated** [Standard]: The transition graph, team composition, routing thresholds, and pruning criteria are control-plane configuration and may be proposed by the self-improvement loop, subject to the risk tiers and gates in Harness §6.2 and §3.6.
* **Admission Persists** [Standard]: After any topology change, the system must still satisfy the admission criteria in §1.2, including beating the single-agent baseline.
* **Evidence and Freezing** [Standard]: Evidence from adversarial simulation (§4.3) and from node-level probes (§6.4) feeds topology changes, and the topology is frozen per release.

## 6. Multi-Agent Evaluation & Judge Alignment
[Who Validates the Validators? arXiv:2404.12272; AutoMetrics: arXiv:2512.17267]
General evaluation principles (multiple trials, transcript vs. outcome, capability vs. regression suites, code-first grading, evaluator fallibility, mocks, and cost-aware CI) are specified in Harness §3.3, §3.4, and §3.6. This section adds the machinery specific to evaluating multi-agent graphs, where errors compound and automated judges cannot be blindly trusted for open-ended domains (e.g., planning, drafting).

### 6.1 Trajectory Evaluation Across Agents
* **Multi-Agent Trajectory Metrics** [Standard]: Measure the efficiency, safety, and logical soundness of the *trajectory* across agents (including search efficiency, critique accuracy, handoff quality, and pruning decisions), not solely the final outcome.
* **Credit Attribution** [Standard]: Evaluation results must be attributable to individual nodes and handoffs, so that failures can be fed to the credit-assignment machinery in §5.1.

### 6.2 Isolated Benchmark Sandboxes (Terminal-Bench Paradigm)
[Terminal-Bench: arXiv:2601.11868] Standard static benchmarks (like MMLU) are insufficient. Evaluation must occur in highly realistic, stateful environments:
* **Interactive CLI Environments** [Standard]: Agents must be evaluated inside containerized terminals where they autonomously navigate filesystems, install dependencies, and run scripts.
* **Open-Ended Verification** [Standard]: Tasks must span complex domains (e.g., distributed systems debugging, reverse engineering). The system must evaluate the agent based on programmatic post-execution tests (verifying the final state of the container).
* **Continuous Benchmark Pruning** [Standard]: Saturated tasks that all models pass are removed per Harness §3.6, and harder tasks are continuously cycled in to track the frontier of agent capability.

### 6.3 Cost-Efficient Rapid Evaluation (tinyBenchmarks Paradigm) [Standard]
[arXiv:2402.14992] Running full benchmarks is cost-prohibitive. As the specific implementation of the Cost-Aware CI requirement in Harness §3.6, the evaluation system must compress massive datasets down to tiny, high-signal subsets using Item Response Theory for rapid CI/CD runs. This capability is a SHOULD, and compressed subsets must be validated against the full suite before they gate anything (Harness §3.6).

### 6.4 The Tripartite Grading System (Node-Specific Probes) [Standard]
The system must deploy three distinct types of grader probes across the network nodes:
* *Code-Based Graders (For Action/Coder Nodes)*: Fast, cheap, and deterministic. Evaluate strictly via static analysis, linters, and dynamic execution (sandboxed outcome verification). Do not use LLMs for this.
* *Model-Based Graders (For Generative/Router Nodes)*: Flexible and nuanced. Use LLM-as-a-judge (with Binary True/False metrics over Likert scales) to evaluate subjective transcripts, tone, or tool-calling behavior.
  * **LLM-as-a-Judge Bias Mitigation** [Standard] [MT-Bench: arXiv:2306.05685]: Automated judges suffer from proven systemic biases. The evaluation harness must programmatically mitigate:
    * *Position Bias*: When comparing two agent outputs, the harness must run the evaluation twice (swapping the order of the outputs) and aggregate the score.
    * *Verbosity Bias*: The grading prompt must explicitly instruct the judge to penalize unnecessary fluff and prioritize conciseness to prevent judges from blindly favoring longer responses.
    * *Self-Enhancement Bias*: To prevent a model from favoring its own outputs, the system should ideally use a different frontier model for the judge (e.g., using Claude 3.5 to judge GPT-4o outputs).
* *Human Graders*: Slow and expensive "gold standard." Used exclusively to calibrate the Model-Based Graders and ensure they aren't hallucinating.

### 6.5 AutoMetrics Synthesis (Mathematical Evaluator Alignment)
*SHOULD: a synthesized metric is validated on a held-out golden set before it serves as a reward or a gate.*
Automated LLM judges inherit the hallucinations and flaws of the models they evaluate. The MLOps suite must implement a strict mixed-initiative alignment pipeline to mathematically synthesize evaluation criteria that agree with human common sense:
1. **Ground Truth Grading** [Standard]: Developers manually grade (Pass/Fail) a highly constrained, "golden" subset of production traces (e.g., < 100 logs).
2. **Candidate Generation & Retrieval** [Standard]: The system automatically uses an LLM to generate multiple *different* automated validators tailored to the human feedback. Simultaneously, it must retrieve standard, pre-built deterministic checks from an external metric library (e.g., MetricBank).
3. **Regression & Synthesis** [Standard]: The system runs all candidate validators and retrieved metrics against the golden subset. It must then use a regression model to mathematically synthesize a weighted combination of these metrics that maximizes correlation (e.g., Kendall correlation) with the human grades.
4. **Proxy Reward Deployment** [Standard]: The synthesized metric is then deployed as a highly accurate "proxy reward" into the DSPy/GEPA optimization pipelines, operating with the same fidelity as a verifiable, deterministic reward.
5. **Iterative Refinement (Managing Criteria Drift)** [Standard]: Evaluation criteria cannot be permanently frozen. The telemetry UI must surface edge cases where the automated judge and human disagree, allowing developers to update their criteria text, adjust the golden grades, and instantly trigger a re-synthesis of the regression model.

### 6.6 Metric Induction from Open-Ended Feedback (AutoLibra Paradigm)
*SHOULD: an induced metric passes the coverage and redundancy meta-metrics and is validated on a held-out golden set before it serves as a reward or a gate.*
[AutoLibra: ICLR 2026 / OpenReview 4BjGVZ7Bxn] Relying solely on pre-defined metrics or binary task success is insufficient for evaluating fine-grained agent behaviors. The evaluation harness must support automatic metric induction:
* **Feedback Grounding** [Standard]: The system must take raw, unstructured human feedback (e.g., user complaints like "the agent clicks disabled buttons") and ground it to specific actions in the agent's execution trajectory.
* **Automated Metric Generation** [Standard]: The system must cluster similar positive/negative behaviors and automatically synthesize a concrete new evaluation metric (including a strict definition and pass/fail examples) for the LLM-as-a-judge to use.
* **Meta-Evaluation** [Standard]: The system must mathematically evaluate its own newly generated metrics using two meta-metrics: **Coverage** (ensuring all user feedback is accounted for) and **Redundancy** (consolidating overlapping metrics to save compute).
* **Self-Regulation via Optimization** [Standard]: These induced metrics must be seamlessly plugged into the DSPy/GEPA optimization pipelines, allowing the agent network to self-regulate and automatically improve against nuanced human preferences rather than blunt success/fail flags.

### 6.7 The Data Flywheel [Standard]
As the multi-agent system runs in production, the framework must automatically log failures (via the node-specific probes) and use those traces to propose updates to the few-shot demonstrations in the agents' prompts, closing the loop from operational monitoring to continual prompt improvement. Proposed updates are control-plane changes and are promoted only through Harness §3.6.

### 6.8 Evaluation Integrity for Multi-Agent Runs
The submission-loop, evaluator, and recovery requirements in Harness §3.4, §3.6, and §5 apply to multi-agent runs. This section adds what multiple agents change.
* **Independent Final Evaluator** [Standard]: The evaluator of a run must not be one of the agents in the topology and must not share its credentials or context (§0.2, rule 4). A judge that reuses a participating agent has low independence.
* **Whole-Run Snapshot** [Standard]: A submission from a multi-agent run snapshots the state of every agent environment and the Hub together, so that the evaluated result corresponds to one consistent moment (Harness §5).
* **Replication Sized for Multi-Agent Variance** [Standard]: Multi-agent runs compound randomness across agents and handoffs. The replication policy for a task must be set from the observed variance of the topology, not copied from a single-agent baseline, and topology comparisons use the confirmatory evaluation in Harness §3.6.
* **Per-Agent Cost Attribution** [Standard]: Tokens, accelerator-hours, and sandbox usage are attributed per agent, so that the cost side of the benefit test in §1.2 can be computed and budget exhaustion can be traced to a node.
* **Cross-Agent Audit** [Standard]: Evaluators may read inter-agent messages and every agent's trajectory (read-only and written by the harness) to detect collusion, sycophancy, and tampering. Those messages are untrusted input to the evaluator (Harness §4.3).
* **Provenance** [Standard]: The run provenance manifest (Harness §3.6) includes the topology version, the team composition, and any pruning decisions (§2.3).

## 7. Data Annotation & Synthesis
This section specifies how the platform annotates data and synthesizes training and evaluation data, for example to distill smaller models or to grow evaluation suites. It uses this document's conversation channels (§2.1) for consensus labeling and depends on the Harness PRD, including its profile tags (Harness §1.2). It is delivered in Train 4 (Harness §1.3). A deployment is at least Standard, and pipelines that run repository code at scale use the isolation tier in Harness §4.1. Sources: Data Annotation Survey (EMNLP 2024, arXiv:2402.13064) and SWE-smith (arXiv:2504.21798).

### 7.1 Data Governance
* **Source Data Masking** [Standard]: Production logs used as source material first pass the privacy-preserving export requirements in Harness §3.7 (PII redaction plus contextual masking of quasi-identifiers), and only workloads that have opted in may contribute.
* **Lineage and Provenance** [Standard]: Every synthetic record carries its generator model and version, its prompt or configuration, its source, and the filters it passed.
* **Output-Use Terms** [Standard]: Before a model's outputs are used as training data for another model, confirm that the terms of use of the generating model permit that use.
* **Contamination Control** [Standard]: Synthetic training data must be disjoint from held-out evaluation sets and tasks, checked with near-duplicate detection against them (Harness §6.4, split discipline).
* **Quality Gates** [Standard]: Every pipeline applies deduplication, a diversity measurement, validity checks (execution-based where possible), and a human review of a sample before data is released.

### 7.2 Instruction Evolution
* **Mutation Operators** [Standard]: Generate diverse and harder training tasks from a minimal set of human-provided seed tasks. The orchestrator prompts a model to mutate each seed with explicit operators: *Constraint Addition* (e.g., "Rewrite the task but enforce a memory limit of O(1)."), *Deepening* (e.g., "Rewrite the task to require a multi-step logical deduction before taking action."), and *Concretizing* (e.g., "Replace general nouns with highly specific, obscure edge cases.").
* **Filtering Gate** [Standard]: A second model call or a deterministic script evaluates each mutated task. A mutation that is identical to its seed or impossible to solve is discarded.

### 7.3 Annotation and Preference Data
* **Rationale Before Label** [Standard]: When the system labels data (e.g., classifying intents or grading agent outputs), it does not output naked labels. The annotator outputs a step-by-step rationale before the final label. Labels are validated against a human-graded sample, and the rationale is retained for audit.
* **Model Contrast Strategy** [Standard]: Route the same prompt to a highly capable model for the "chosen" response and to a cheaper or untuned model for the "rejected" response.
* **Flaw Injection Strategy** [Standard]: With a single model, produce the "chosen" response, then instruct the model to rewrite it with a specific injected flaw (e.g., a subtle off-by-one error) to produce the "rejected" response.
* **Preference Artifact Check** [Standard]: Pairs built by contrast or flaw injection differ from natural preference pairs in distribution. Validate any preference model trained on them against held-out, human-labeled pairs.

### 7.4 Consensus Labeling
* **Debate Protocol** [Standard]: For ambiguous or complex data (e.g., security vulnerabilities), route the item to at least two agents with contrasting roles (for example, an attacker and a defender) over a conversation channel with a declared maximum number of rounds and a stop criterion.
* **Consensus Judge** [Standard]: After the debate, a judge that is independent of both debaters (Harness §3.4) synthesizes the arguments and outputs the label. Agreement statistics are recorded, and a human audits a sample of items, especially those with low agreement.

### 7.5 Execution-Verified Task Generation
* **Automated Sandbox Provisioning** [Standard]: Given a target repository, the orchestrator constructs an isolated, containerized environment with its dependencies and test suite. Repository code runs as untrusted code under Harness §4.1, with egress denied by default and dependencies fetched only through approved mirrors at the policy proxy (Harness §4.3).
* **Bug Synthesis** [Standard]: Synthesize tasks by identifying passing tests and mutating the code to force a failure, so that the agent's objective is to restore a passing state. A task is admitted only if its tests fail before the reference fix and pass after it.
* **Scaling Under Budgets** [Standard]: The pipeline must scale to tens of thousands of deterministic, sandbox-verified tasks without human intervention, within compute and cost budgets (Harness §3.3). Tasks are deduplicated, and tasks that a model can solve by recalling the original repository are flagged.
